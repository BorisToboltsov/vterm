# ADR 0071 — Сценарии: рецепты, проекты Ansible и Terraform

**Статус:** принято (готовится).

## Контекст

Владелец попросил библиотеку скриптов и сценариев «например в формате Ansible и Terraform» для
настройки серверов — с готовыми, своими и загруженными, с запуском из приложения — и предложил два
пути: отдельное окно вместо терминала со списком файлов сценария и редактором (пример 1) или
папку в SFTP, которая сама узнаётся как проект Ansible или Terraform, с подсветкой и кнопкой
запуска на выбранных серверах (пример 2).

Сравнили, кто так умеет:

- **Termius** — сниппеты, запуск на нескольких хостах, переменные через окружение хоста. Ни
  проверки, ни итога по хостам, ни Ansible.
- **XPipe** — скрипты, пакетный режим на выбранных системах. Параметров и итога по хостам нет.
- **Warp** — YAML-workflow с аргументами и значениями по умолчанию. Один терминал, не серверы.
- **Semaphore UI, AWX** — шаблоны Ansible и Terraform, инвентари, логи прогонов. Веб-сервер для
  команды, а не клиент на рабочем месте.
- **Ansible для VS Code** — запуск playbook из меню, вывод в терминал. Без структуры прогона и
  связи с серверами.
- **ansible-navigator** — прогон с переходом play → задачи → хосты (по событиям `ansible-runner`).
  TUI, выбора целей нет.

Пустое место: SSH-клиент, в котором каталог серверов — это инвентарь, проект лежит там же, где
работают (на сервере или локально), а прогон виден структурно, без сети со стороны приложения.
Владелец выбрал все рекомендованные ответы по рендерам (решения 1А–11А ниже).

## Решение

**Три части, одно окно запуска (1А).** Свои рецепты vterm; проекты Ansible целиком; проекты
Terraform — подсветка, обзор и план.

**Где живёт (2А, гибрид).** Пример 2 — основа: панель файлов узнаёт папку по именам (`project.ts`:
`ansible.cfg`, `group_vars`/`host_vars`/`roles` рядом с playbook, playbook рядом с инвентарём;
`*.tf` или lock-файл) и ставит над списком полосу «Проект Ansible ›  Пробный · Запустить…» /
«Проект Terraform ›  План» с булавкой. «Обзор» — документ соединения без текста (`EditorDoc.project`,
как карта пайплайнов ADR 0068): стоит в зоне файлов рядом с терминалом, не открывается после
перезапуска. Пример 1 получается сам, без нового вида центра: закладка проекта в панели
«Сценарии» открывает вкладку своего места, панель файлов в папке и обзор рядом с терминалом.
Панель «Сценарии» — глобальная, как дерево серверов (`isSessionPanel` — ложь): работает без
вкладок, по умолчанию в нижнем доке; вкладки «Библиотека | Прогоны».
Отвергнуто: «режим проекта» вместо терминала — вкладка центра, которая не соединение, ломала бы
ADR 0024 и дублировала панель файлов и редактор.

**Рецепт (3А) — обычный `.sh` с шапкой `# vterm:`**: имя, описание, системы, нужен ли root, умеет
ли проверять, параметры (`NAME: { label, default, type: text|bool|secret, required, hint }`).
Тело — функции `check` (0 — уже так, 1 — изменит, печатает что) и `apply` и последняя строка
`case "${VTERM_MODE:-apply}" in check) check ;; *) apply ;; esac`: файл запускается и без vterm.
Отвергнуто: YAML со списком шагов (Warp, Rundeck) — уже не скрипт; библиотека только из playbook —
нужен Ansible на узле запуска.

**Как рецепт доходит до серверов (4А) — SSH самого vterm.** Ключи, пароли из keychain, jump host,
проверенные ключи хостов — как у вкладки. Сессия — открытая или вкладка, открытая обычным путём
(вопрос о пароле, ключ хоста), фокус остаётся на месте; не подключилась за 60 с — сбой этого
сервера в прогоне. Исполняет фиксированная обёртка (`scenarios::run_command`): скрипт и пароль sudo
идут через stdin (`sudo -S`, без пароля — `sudo -n`), скрипт — во временный файл `umask 077`,
который обёртка удаляет при любом исходе, и запускается с закрытым stdin (команда скрипта, читающая
stdin, иначе съела бы остаток скрипта). Параметры экспортируются в начале скрипта. Шесть серверов
одновременно, «Выполнить» сперва проверяет и пропускает сервер, где всё уже так; остановка —
`sftp_cancel`. В запись сессии — имя рецепта и ответ (`[script]`), не сам скрипт.
Отвергнуто: фоновые соединения без вкладок, как у Termius, — новое понятие бэкенда со своим входом.

**Цели Ansible (5А).** Инвентарь проекта, как его видит сам Ansible (`ansible-inventory --list`),
сверяется с каталогом: хост по адресу и порту, иначе по имени — прод узнаётся, как бы он ни был
записан. «Из каталога» — временный инвентарь (адрес, порт, логин; файл ключа и jump host — только
на этом компьютере); паролей в нём нет — сервер с паролем спросит Ansible (`-k`). Без Ansible на
узле INI-инвентарь читается самим vterm, и так и сказано.

**Где запускается (6А) — там, где лежит проект**, в терминале этого соединения (принцип 3): на
сервере сессии или на этом компьютере. Строка — POSIX (`cd … && env … ansible-playbook …`); Ansible
на Windows — только в WSL, не POSIX-оболочка — отказ с объяснением. Terraform — `terraform
-chdir=…`, строка — под оболочку вкладки (`renderArgv`).

**Вид прогона (7А) — по событиям самой Ansible.** Сборщик vterm (`vterm_events.py`, notification
callback с `CALLBACK_NEEDS_ENABLED = False`) кладётся во временную папку прогона и находится через
`ANSIBLE_CALLBACK_PLUGINS` (пути по умолчанию сохранены): пишет JSON-строки play, задач, результатов
по хостам, diff и итога в `$VTERM_EVENTS`. Вывод Ansible остаётся в терминале как был; результаты
приходят к сборщику уже очищенными (`no_log`), сообщения и diff обрезаны. Вид читает файл целыми
строками (`iac_read`), задачи × хосты, итог, ячейка — с сообщением и diff, ошибку — в ИИ.
Прогон кончился — папка удаляется сразу (события уже в памяти), закрытие вкладки — остальное.
Отвергнуто: разбор вывода по тексту — ломается от `stdout_callback` в `ansible.cfg`.

**Пробный прогон (8А)** — первая кнопка везде: `--check --diff` у Ansible, `check` у рецепта.
Применение с продом среди целей — красным и после вопроса; после пробного — «Применить без
--check…» с тем же выбором.

**Terraform.** Обзор из текста `.tf` (сканер блоков, не парсер HCL), версии — из lock-файла,
`terraform version`. «План» — `terraform plan -out=<папка прогона>/plan.tfplan` в терминале; когда
файл перестал расти — `terraform show -json` и вид по модулям: создать, изменить, заменить,
удалить, атрибуты изменения; помеченное `sensitive` не показывается никогда, неизвестное — «станет
известно после apply». «Применить план…» — ровно сохранённый план (`terraform apply <plan>`), после
вопроса; удаление и замена — красным. Состояние (state) приложение не читает никогда.

**Встроенная библиотека (9А)** — 10 рецептов в сборке: Docker, обновление пакетов, пользователь с
ключом, порт в firewall, swap, часовой пояс и NTP, fail2ban, вход только по ключу, node_exporter,
очистка диска; имена и подписи — на языке интерфейса (`t()`), файл — с английской шапкой. Плюс
заготовка «Новый проект Ansible» с инвентарём выбранных серверов.

**Где хранятся свои (10А).** Папка `scripts` в данных приложения (её рецепты — в полном бэкапе,
раздел `scripts/`; занятое имя при импорте не перезаписывается) и любые папки этого компьютера как
источники — например, свой git-репозиторий (только чтение, удаления нет).

**ИИ (11А).** «Спросить ИИ» об упавшем сервере рецепта и упавшей задаче — через `askAbout`
(маскирование и согласие); скрипт, который ИИ делает из записи, — «В библиотеку» из редактора.

**Сеть (принцип 6).** Приложение ничего не скачивает: встроенное — в сборке, зависимости ставит
кнопка, которая печатает `ansible-galaxy install -r requirements.yml` в терминал. Трафик делают
программы пользователя на хосте проекта — `ansible`, `ansible-inventory` (динамический инвентарь),
`terraform` — как `gh`/`glab` в ADR 0069. Проверки проекта идут командой `iac_run` под политикой
(`scenarios::check_iac_args`): `--version`, `ansible-inventory --list -i <путь>`, `ansible-galaxy
collection list`, `terraform version`, `terraform show -json` только плана из папки прогона —
ничего, что меняет серверы или читает state.

## Не взято

- **Расписание, прогоны по cron, история прогонов на диске.** Это AWX и Semaphore; прогоны живут,
  пока работает приложение.
- **Galaxy и реестр модулей внутри приложения** — сеть приложения; ставит пользовательский
  `ansible-galaxy` в терминале.
- **Сравнение known_hosts узла запуска с ключами vterm** — нужен `ssh-keygen -F` на каждом хосте;
  ключи проверяет OpenSSH там, где запущен Ansible, и так и написано.
- **ansible-lint по всему проекту в обзоре** — есть линт открытого файла в редакторе.
- **Выводы Terraform → в каталог серверов, цепочка Terraform → Ansible** — следующим шагом.

## Последствия

- Rust: `scenarios.rs` (библиотека, обёртка рецепта, политика проверок, временная папка прогона),
  мост `commands/scenarios.rs` (`recipe_run`, `iac_run`, `iac_temp`, `iac_read`, `iac_cleanup`),
  источник диагностики `scenarios`, раздел бэкапа `scripts/`.
- Фронт: подсистема `src/lib/scenarios/` (чистые `recipe`, `recipelib`, `project`, `inventory`,
  `ansibleplay`, `ansibleargv`, `ansibleevents`, `tfproject`, `tfplan`, `scaffold`, `bookmarks`;
  компоненты `ScenariosPanel`, `RecipeDetail`, `ProjectView`, `AnsibleRunDialog`, `AnsibleRunView`,
  `TfPlanView`, `NewProjectDialog`, `TargetPicker`), стор `stores/scenarios`, режим HCL
  `editor/hclmode.ts`, `PanelId` `scenarios`, настройки `scenarioSources`/`scenarioProjects`/
  `scenarioTab`.
- Гейты: `scenarios.guard`, `vterm/owned-imports` (команды сценариев — только стор), Rust
  `what_the_checks_of_a_project_run_is_allowed`, `a_recipes_script_and_password_never_reach_a_command_line`.
