# ADR 0068 — Схема пайплайна: GitHub Actions и GitLab CI до пуша

**Статус:** принято (готовится).

## Контекст

Владелец попросил: указать на файл или группу файлов пайплайна и увидеть схему — этапы, задачи,
связи — и то, как пайплайн пройдёт. Сравнили, кто так умеет:

- **GitLab, редактор пайплайна.** «Visualize» рисует этапы колонками и `needs` линиями, «Validate»
  проигрывает создание пайплайна для ветки по умолчанию и ловит ошибки `rules` и `needs`, «Full
  configuration» показывает конфиг со всеми `include`. Только в вебе и только GitLab.
- **GitHub** рисует граф задач уже запущенного прогона; до пуша — ничего.
- **`act -g`** рисует ASCII-граф workflow для события; **workflow-editor для VS Code** — узлы и рёбра
  по `needs` с триггерами. Только GitHub.

Пустое место: GitHub и GitLab вместе, до пуша, офлайн, по файлу на сервере за SSH, с ответом «что
запустится при таком событии». Владелец выбрал рекомендованные решения (отмечены ниже), макеты
одобрены — «как в git, со связями с правильными загибами, симуляция событий с анимацией».

## Решение

**Где.** Два места, один компонент графа.
- **Вид файла в редакторе: «Код | Схема | Рядом».** Пайплайн узнаётся по пути (`.github/workflows/`,
  а также `.gitea/` и `.forgejo/` — тот же формат; `.gitlab-ci.yml` и `*.gitlab-ci.yml`), фрагмент
  GitLab (`ci/test.yml`) — по тому, что в нём. Схема читает буфер редактора: правка видна сразу.
  «Рядом» связывает код и схему: курсор выбирает задачу, выбранная задача подсвечивает свои строки,
  «Открыть в коде» ведёт к строке — своей или включённого файла. CodeMirror остаётся смонтированным
  при любом виде: отмена, курсор и прокрутка не теряются.
- **Вид «Пайплайны» для группы.** Пункт «Схема пайплайнов» в меню панели файлов — на папке
  workflows, на `.github`, на корне репозитория (меню фона, когда там есть пайплайны) и на
  нескольких выбранных файлах. Это документ соединения без текста (`EditorDoc.pipelines`): стоит в
  зонах, как файлы, уезжает с вкладкой в другое окно, но после перезапуска не открывается — его
  читают заново из файлов. Карта: события слева, пайплайны посередине, вызываемые — справа; вызов
  (переиспользуемый workflow, дочерний пайплайн) — пунктир со стрелкой, `workflow_run` — «после».
  Щелчок по пайплайну — его граф, «Открыть файл» — в редакторе.

**Что читается.** Всё локальное в репозитории: GitLab `include: local` (и шаблон `*` в одной папке),
дочерние пайплайны `trigger: include`; GitHub — свои переиспользуемые workflow `./…yml` (и `$/…yml` — тот же репозиторий) и
composite actions `./…/action.yml` (их шаги — в задаче). Читает тот же транспорт, что открыл файл
(`connectionFiles`: SFTP сессии или этот компьютер), с пределами — 40 файлов, вложенность 4.
Чужое — `project:`, `remote:`, `template:`, `component:`, workflow другого репозитория — **не
скачивается** (принцип 6) и названо «не прочитан: вне этого репозитория».

**Как разбирается.** GitLab — как его читает GitLab: включённое под главным файлом, `extends`
глубоким слиянием (словари сливаются, списки и значения заменяются, свои ключи важнее), `!reference`,
`default:` и `inherit:`, скрытые `.шаблоны`, `stages` (`.pre`/`.post` — когда заняты), `needs` с
`optional`, `parallel` и `parallel: matrix`, `when`, `allow_failure` (у ручной задачи без `rules` —
по умолчанию да, как в GitLab). GitHub — `on:` со всеми фильтрами, `needs`, матрица с `include` и
`exclude` по правилам GitHub, `if:`, `environment`, `continue-on-error`. Проблемы файла — списком:
`needs` на несуществующую задачу, круг `needs`, `needs` на более поздний этап, неизвестный этап,
неизвестный `extends`, пустой `!reference`, нечитаемые файлы, матрица из выражения.

**Симуляция события (решение 2б).** События — колонка слева в самой схеме (те, что называют
триггеры; у GitLab — push, merge request, тег, расписание, вручную), общей шиной к задачам, с
которых пайплайн начинается; ветку или тег можно вписать. Колонка задач не шире карточки: без неё
workflow из независимых задач (как `ci.yml` vterm) выглядел списком полос во всё окно. GitHub:
фильтры `on:`, затем `if:` каждой задачи над контекстом события; задача, чья `needs` пропущена,
пропускается, если её `if:` не проверяет статус (`always()` и т. п.). GitLab: `workflow: rules`,
затем `rules` (первое совпавшее) или `only`/`except` — по умолчанию `[branches, tags]`, поэтому
задача без правил не идёт в пайплайн merge request; `needs` на выпавшую задачу без `optional` —
пайплайн не создаётся, ровно как отвечает GitLab. Выражения разбирает свой парсер (без `eval`):
трёхзначная логика, неизвестное названо — секреты, переменные проекта, изменённые файлы
(`changes`, `paths`), ветка-источник merge request. «?» — не пропуск и не запуск.

**Проигрывание.** Волнами: волна запускает каждую задачу, чьи зависимости кончились. Это **порядок,
а не время** — длительностей в файле нет, поэтому каждая задача идёт один шаг. Ручная задача и
окружение (`environment` — одобрение, если у окружения есть правила защиты) останавливают свою
часть прогона до кнопки. Ручная задача GitLab без `rules` дальнейших этапов не держит.

**Прогон группы — дорожками (решение владельца по макетам).** Карта показывает устройство, а не время:
вызов идёт посреди пайплайна, и по вертикальной стопке карточек порядок не читается. «Проиграть»
превращает каждую карточку, до которой дошло событие, в дорожку на всю ширину, а её задачи вылетают
в колонки волн, общих для всей группы. Вызов, которого ждут, — дорожка прямо под вызвавшим: линия
уходит в неё и возвращается к задачам, ждавшим вызова. Ждут переиспользуемый workflow и дочерний
пайплайн GitLab с `strategy: depend` или `mirror`; без стратегии задача-триггер кончается, как только
пайплайн создан, и вызвавший идёт дальше. Пайплайн, вызванный из двух мест, получает две дорожки;
`workflow_run` — дорожку под тем, после чьего конца стартует. Не запущенные событием стоят строкой
«Не запускаются» внизу. Дорожки остаются после прогона, «Карта» возвращает карточки. Колонку задачи и
её ход в проигрывании считает один список того, что она ждёт (`pipelanes.ts`), поэтому колонка и есть
ход. Отвергнуто: выстроить в линию сами карточки. Порядок пайплайнов так виден, но вызвавший пришлось
бы резать на «до» и «после вызова», а задачи внутри карточки снова стояли бы списком.

**Как рисуется (решение 9).** Своя раскладка в `.ts`: колонки — этапы GitLab или глубина по `needs`;
задача тянется на уровень того, чего ждёт, поэтому большинство связей прямые; связь в соседнюю
колонку поворачивает один раз в желобе (входящие в задачу сходятся на одной линии), дальняя идёт
по свободному зазору между строками и не проходит через задачи; каждый поворот — одного радиуса,
как у линий истории Git. Цвета — токены темы. При смене колонок задачи доезжают, линии гаснут и
появляются на новых местах (путь SVG в WKWebView плавно не меняется). Связи прогона — `ok`,
текущие — бегущим пунктиром. «Скопировать как Mermaid» — текстом (решение 6).

**Парсер YAML (решение 9)** — библиотека `yaml` без зависимостей, грузится при первой схеме (правило
`vterm/lazy-import`): якоря, `<<`, свой тег `!reference`, номера строк. Текст недоверенный: не
больше 200 развёрнутых алиасов, дубли ключей — ошибка, имена — текст, не разметка; шаблон из
`=~ /…/` с вложенными кванторами или длиннее 200 знаков не выполняется — «?».

## Не взято

- **Панель дока «CI»** и **утилита «вставь YAML»**: панель дублирует вид в редакторе и требует
  ширины, которой у дока нет; утилита не видит ни файлов, ни `include`.
- **Mermaid или ELK для отрисовки.** Тяжёлые, Mermaid вставляет стили мимо CSP с nonce, оба не в
  визуальном языке приложения. Экспорт в Mermaid — да, отрисовка — нет.
- **`changes:`/`paths:` из `git diff` сессии (решение 2в).** Возможно, но требует выбрать базу
  сравнения для каждого события; пока «?» с названной причиной.
- **Настоящие прогоны через `gh`/`glab` (2г)** — новое сетевое исключение, отдельным ADR.
- **Точка входа ИИ «объясни пайплайн» (решение 7)** — не в этом выпуске.
- **`exists:` по листингу репозитория.** Асинхронная проверка на каждое событие; пока «?».

## Последствия

- Подсистема `src/lib/pipeline/`: модель, разбор GitHub и GitLab, загрузчик с внедрённым читателем, прогон группы дорожками (`pipelanes.ts`),
  вычислитель выражений, симуляция, проигрывание, раскладка, карта группы, Mermaid — чистые `.ts`;
  компоненты `PipelineGraph`, `PipelineView`, `PipelinesTab`.
- Новых команд Rust нет: файлы читают те же `sftp_read_text`/`read_local_text`/`sftp_list`/`local_list`.
- Гейты: правило `vterm/lazy-import` и `pipeline.guard` (чтение только через читатель соединения,
  ни одного `{@html}` в подсистеме, CodeMirror не размонтируется при смене вида).
