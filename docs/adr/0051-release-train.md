# ADR 0051 — Выпуски по расписанию: поезд из main, хотфикс от тега

**Статус:** принято (v1.32.0).

## Контекст

До 1.32 версию поднимал каждый PR (пункт DoD «версия поднята»), а тег ставился, когда хотелось.
С 6 октября по 4 ноября 2026 вышло 30 minor — от 1.1 до 1.31; тегов к тому моменту 35, опубликован 21
релиз, пять черновиков (1.18.0, 1.18.2, 1.22.0, 1.25.8, 1.25.10) так и остались черновиками.
Номер версии считал шаги разработки, а не выпуски: пользователь видел 1.1.11 → 1.17.1 → 1.19.0 без
системы, и автору это не нравилось так же, как пользователям.

Заодно выяснилось, что «Что нового» в релизе пустое с ~1.20: шаг `release.yml` брал из CHANGELOG
только пункты с жирным заголовком, а записи писать так перестали. Встроенная проверка обновлений
показывает описание релиза — пользователь видел в приложении одну ссылку на CHANGELOG.

Что уже было и что сохраняется: `main` всегда зелёный (ruleset — PR, пять проверок, линейная
история), релиз собирается только по тегу и только после CI и глубоких проверок, черновик
публикует человек.

## Решение

**Изменения копятся в `main`, раз в неделю из них режется одна версия.**

- PR пишет в верхнюю секцию CHANGELOG «## Готовится», в «### Новое» или «### Исправлено», и
  версию не трогает. Обязательная джоба `web` сверяет PR с базой: версию и секции `## vX.Y.Z`
  меняют только ветки `release/*` и `hotfix/*`.
- `train.yml` по понедельникам (и по кнопке): есть пункт в «Новое» — следующий minor, только
  «Исправлено» — patch, пусто — выпуска нет. Поезд поднимает версию `set-version.mjs`, даёт секции
  номер и дату и открывает PR выпуска с автослиянием — тот проходит обычный CI.
- Слитый PR выпуска — push в `main`: тег ставится на коммит, который поднял версию, и только на
  него. Тег запускает прежний `release.yml`.
- Хотфикс — мимо расписания: ветка `hotfix/*` от тега выпуска, patch, тег руками, затем PR в
  `main`.
- Релиз остаётся черновиком. Описание пишет `integrity` один раз: «Что нового» — секции от
  последнего опубликованного релиза, затем как запустить.

Логика — чистые функции [release-train.mjs](../../scripts/release-train.mjs), их и разводку
workflow держит гейт `releasetrain.guard`.

## Альтернативы

- **Ветка-накопитель (`develop` → `main` по расписанию, GitFlow).** `main` и так не выпускает
  сам — выпускает тег; вторая долгоживущая ветка удвоила бы прогоны CI, добавила бы слияния
  назад и конфликты с линейной историей ruleset. Для одного разработчика — расходы без выигрыша.
- **Без новых секретов: `main` всегда держит версию следующего выпуска, бот только ставит тег.**
  Тег от `GITHUB_TOKEN` не запускает `release.yml`, но `workflow_dispatch` запустил бы. Цена: первый
  PR после выпуска обязан поднять версию, дата в CHANGELOG — плановая, пропуск или сбой поезда
  правится руками. Отвергнуто: автоматизация неполная, а правила хрупкие.
- **release-please / changesets.** Делают то же через «PR выпуска», но ведут свой CHANGELOG по
  conventional commits и свою разноску версии — у vterm CHANGELOG рукописный, по-русски и встроен в
  приложение, а версию разносит `set-version.mjs` под гейтом. Сторонний экшен с правом записи —
  ещё одна точка цепочки поставки.
- **Плановый выпуск — всегда minor.** Проще, но выпуск из одних исправлений назывался бы
  «новой функциональностью»; вид по содержимому честнее и стоит одной функции.
- **Публиковать без человека.** Отвергнуто автором: черновик остаётся последней проверкой.

## Последствия

- PR выпуска и тег делает GitHub App, а не `GITHUB_TOKEN`: события `GITHUB_TOKEN` не запускают
  других workflow, PR остался бы без CI. Ключ App — новый секрет с правом записи: он лежит в
  окружении `release` (только `main`), его получают две джобы после бесключевых, решивших, что он
  нужен; в этих джобах не ставится зависимостей, токен не оседает в `.git/config`
  ([SECURITY.md](../../SECURITY.md#цепочка-поставки-ci)). Разовая настройка — в
  [CI.md](../CI.md#один-раз-github-app-выпуска).
- Пока открыт PR выпуска, правка «Готовится» в `main` даёт конфликт в CHANGELOG: окно — время
  одного прогона CI.
- Неопубликованный черновик не теряет изменений: следующее «Что нового» начинается с последнего
  опубликованного.
- Обновление Dependabot без записи в «Готовится» выпуска не вызывает — уедет со следующим;
  исправление уязвимости, которое не может ждать, — хотфикс.
- Пункт DoD «версия поднята» заменён записью в «Готовится»; этап рефакторинга — PR в `main`, а не
  patch-выпуск.
