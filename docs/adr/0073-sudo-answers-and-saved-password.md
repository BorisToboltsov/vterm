# ADR 0073 — sudo: ответ сервера словами, пароль знает только бэкенд, пароль sudo в keychain

**Статус:** принято (готовится).

## Контекст

Владелец правил файл в редакторе. Прав sudo у его пользователя не было. Окно после проверки
сказало только «Не удалось проверить sudo», а у кнопки «Сохранить» осталось «Нужны права» с
предложением проверить sudo снова. Он попросил говорить, что прав нет, и спросил, какие ещё
ответы стоит различать. Вторая просьба — не вводить пароль sudo в редакторе каждый раз, а
подставлять его из keychain.

Что было в коде:

- `check_sudo` возвращала `bool`. Её `sudo -S -p '' true && printf __VTERM_OK__` не различала
  неверный пароль, отсутствие прав, отсутствие sudo и `requiretty`. Сообщения sudo были на языке
  сервера.
- Разбор ответа sudo уже был, но только у панели файлов, работающей под другим пользователем
  (`fileuser::sudo_refusal`, ADR 0047). Он различал «нужен пароль», «неверный» и «отказ» с текстом.
- Пароль sudo держало окно: `EditorDoc.sudoPassword`, поле групповой правки, поле рецепта, поле
  установки инструмента. Он шёл с каждым вызовом (`sftp_read_text`, `sftp_write_text`, линт,
  nginx) и уезжал в пакете вкладки в другое окно.
- Копия `.bak` при сохранении от root собиралась как `sudo if test -e …; then cp …; fi`. sudo
  запускает программы, а `if` — синтаксис шелла: строка была синтаксической ошибкой. С
  включённым «Хранить копию .bak» каждое сохранение от root падало.

Что отвечает sudo 1.9.15 (Ubuntu 24.04) под `LC_ALL=C` — снято на стенде `e2e/sudo`:

| Случай | Ответ |
|---|---|
| верный пароль, `-k -S -v` | exit 0 |
| неверный пароль | `Sorry, try again.` / `sudo: no password was provided` / `sudo: 1 incorrect password attempt` |
| `-n -v`, нужен пароль | `sudo: a password is required` |
| нет прав, `-n -v` — ещё **до** пароля | `Sorry, user plain may not run sudo on <host>.` |
| права только на `id`, `cp` | `Sorry, user limited is not allowed to execute '/usr/bin/cp …' as root on <host>.` — и `-v` при этом проходит |
| `requiretty` | `sudo: sorry, you must have a tty to run sudo` |
| нет sudo (через `env`) | `env: 'sudo': No such file or directory`, exit 127 |
| `sudo cat … \| head -c N` при отказе | отказ только в stderr, **exit 0** — у конвейера код `head` |

Как это сделано у других:

- **VS Code Remote-SSH** — «Retry as Sudo» есть только локально. На сервере — расширение «Save as
  Root», пароль вводится каждый раз.
- **WinSCP** — sudo только через `sudo -S sftp-server` и только с NOPASSWD.
- **Termius, Royal TS** — пароль sudo не хранят. В Royal TS учётные данные подставляются при
  подключении, не для sudo.
- **Ansible** — `become_password` из vault или `-K` на каждый прогон. Пароль входа как пароль
  sudo — обычная практика (`ansible_become_password: "{{ ansible_password }}"`).

## Решение

Владелец взял все рекомендованные варианты.

**1. Ответ sudo читается в одном месте.** `sudo::answer` разбирает слова sudo под `LC_ALL=C`
(шаблон `fileuser.rs`) и возвращает три вида ошибок, которые окно различает:

- `sudo-password: <что отклонено>` — нужен пароль: `nothing`, `saved` или `login`;
- `sudo-rejected` — неверный пароль;
- `sudo-refused: <почему>: <что сказал sudo>` — отказ при любом пароле: `not-allowed`,
  `command-refused`, `no-sudo`, `needs-tty`, `account-locked`, `password-expired`, `no-answer`,
  `other`.

Нераспознанное приходит как `other` со словами сервера — принцип 5, без правдоподобных догадок.
Тем же разборщиком пользуются панель файлов, редактор, установка инструментов и рецепты.
Отвергнуто:

- угадывать права по группам `sudo`/`wheel` — sudoers даёт права и поимённо;
- разбирать ответ на фронте — бэкенд видит stderr и код выхода, фронт видит только строку ошибки.

**2. Проверка — `sudo -v`, без пароля — `-n`.** `-k -S -p '' -v` проверяет пароль и ничего не
запускает. `-k` нужен, чтобы оставшийся тикет sudo не выдал неверный пароль за верный. Без пароля
sudo запускается с `-n`, а не с пустым Enter. Пустая строка — это попытка с пустым паролем: строка
в auth.log и шаг к блокировке через `pam_faillock`.

Проба `sudo -n -v` при открытии файла, который нельзя записать, ничего не тратит. При этом она уже
говорит «нет прав» у пользователя вне sudoers. Поэтому значок у «Сохранить» знает ответ до того,
как пользователь начал править.

Чтение от root (`sudo cat | head`) смотрит на stderr при пустом stdout (`read_refusal`). Иначе
отказ выглядел бы пустым файлом. Шаги записи разбираются по коду выхода (`sudo_step`). Копия
`.bak` идёт через `sh -c` (`sudo_backup_step`).

**3. Пароль sudo знает только бэкенд (2А).** Окно отдаёт введённый пароль один раз — в
`sudo_check`, единственную команду моста, которая принимает пароль sudo. Подошедший пароль
сессия запоминает в `SudoMemo`, внутри `SshSession`: память умирает вместе с сессией и чистится
без отдельного кода в `end_session`.

Остальные шаги sudo этой сессии берут пароль оттуда: чтение и запись от root, линт, nginx, «панель
под пользователем», установка инструмента, рецепт. Из окна ушли `EditorDoc.sudoPassword` и пароль
в пакете вкладки. Гейт `a_sudo_password_reaches_the_backend_only_through_the_check` держит, что
другие команды моста пароль не принимают, а сохранённый пароль sudo читает только
`commands/sudo.rs`.

**4. Порядок паролей (3: А + Б).** Если ничего не введено, бэкенд пробует по порядку:

1. что sudo уже взял в этой сессии;
2. без пароля (NOPASSWD);
3. пароль sudo, сохранённый в keychain (`vterm:sudo`, по id сервера);
4. пароль входа из keychain, если вход по паролю.

Каждый сохранённый пароль — не больше одного раза за сессию. Отклонённый помечается, и следующий
вопрос говорит, какой не подошёл: «Пароль из keychain больше не подходит», «Пароль входа к sudo
здесь не подошёл».

Пароль входа — не новая утечка: сервер получил тот же пароль при входе. Отвергнуто:

- пробовать сохранённые пароли на каждом шаге — каждая ошибка считается faillock'ом;
- подставлять пароль в поле окна — `PasswordInput` не заполняется заранее (инвариант), и пароль
  оказался бы в WebView;
- Touch ID перед использованием — отложено, нужна нативная часть на двух ОС.

**5. Сохранение — галочкой после согласия sudo.** «Запомнить в keychain для user@сервер» включена
по умолчанию, как у пароля входа. Пароль пишется только после того, как sudo его принял.
`ServerProfile.hasSavedSudo` — подсказка для формы: «Пароль sudo сохранён». «Забыть сохранённый
пароль» удаляет и его. Бэкап его не несёт, импорт считает сохранённым только то, что есть в этом
keychain.

Пароль, введённый для рецепта или групповой правки, не запоминается. Он идёт только на те серверы,
где свой пароль не подошёл.

**6. Где sudo не нужно вводить, сохранение идёт само — кроме прода.** Если sudo ответил, что
пароль не нужен или есть сохранённый, «Сохранить» у файла без прав пишет через sudo. На проде тот
же путь требует одного явного «да» с названием источника пароля (принцип 7). Повышение прав никогда
не происходит молча.

Отказ sudo меняет «Сохранить» на «Сохранить копию…». У кнопки появляется плашка с причиной, ответом
сервера и выходом. Пока файл правится от root, рядом с путём стоит чип `root`.

## Последствия

- Владелец видит причину: «Нет прав sudo · только чтение», «sudoers не пускает эту команду», «На
  сервере нет sudo», «sudo требует терминал», «Учётная запись заблокирована», «Пароль истёк»,
  «sudo не ответил». Неверный пароль остаётся внутри окна пароля.
- Пароль sudo больше не живёт в памяти WebView и не ездит между окнами. Цена — пароль, введённый
  для одного файла, действует для всей сессии. Это та же граница, что у тикета sudo на сервере.
- Пароль sudo в keychain — та же поверхность, что пароль входа там же (SECURITY.md).
- Групповая правка и рецепты на многих серверах больше не требуют одного пароля на всех: у
  каждого сервера свой.
- Копия `.bak` от root действительно создаётся.
- Живые тесты `live_sudo` на стенде `e2e/sudo` (добавлены аккаунты `limited` и `ttyonly`)
  повторяют таблицу ответов и порядок паролей.
- С несколькими логинами у сервера ключ keychain станет ключом логина. Этот ADR оставляет ключ
  сервера.
