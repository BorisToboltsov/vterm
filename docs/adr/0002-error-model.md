# ADR 0002 — Единый тип ошибок `AppError`

**Статус:** принято (Фаза 6.3).

## Контекст

Команды бэкенда возвращали `Result<T, String>`. Строковые ошибки нетипизированы,
а два случая — отказ аутентификации и недоверенный host-key — несут «маркеры»,
которые фронтенд распознаёт по подстроке, чтобы переспросить секрет.

## Решение

Ввести `error::AppError` (`thiserror`) и `AppResult<T>`:

- семантические варианты `AuthRejected`, `HostKeyRejected`, `NoSession`,
  `UnknownServer`; всё остальное — `AppError::Message(String)`;
- `From<String>/<&str>/<io::Error>/<serde_json::Error>` — чтобы существующие
  `?` и `.map_err(|e| format!(…))?` продолжали работать без переписывания;
- `Serialize` сериализует ошибку в строку сообщения — **контракт с фронтендом
  не меняется** (invoke по-прежнему отклоняется строкой, маркеры сохранены в
  `Display`).

## Последствия

- Типобезопасные категории ошибок и единая точка их эволюции.
- Нулевое изменение на фронтенде; тест `error.rs` фиксирует наличие маркеров и
  строковую сериализацию.
- Дальнейшие места можно постепенно переводить с `Message` на точные варианты.
