# ADR 0070 — Пайплайны в панели CI: вкладки «Пайплайны | Прогоны»

**Статус:** принято (готовится).

## Контекст

Схема пайплайна (ADR 0068) и панель «CI» (ADR 0069) — одна возможность, разрезанная пополам.
Панель начинается с прогона, схема — с файла; общее у них — файл workflow, но в панели файла как
записи нет. Из панели к схеме вела одна кнопка «На схеме» в карточке уже выбранного прогона, карта
группы открывалась только из меню панели файлов. Человек, зашедший в репозиторий, не видел, что
схема и симуляция есть. Хуже того: без `gh`, без входа, без remote панель показывала пустой экран,
хотя схеме и симуляции форж не нужен вовсе.

Сравнили, как у других:

- **GitHub в вебе** — слева список workflow (файлов), справа их прогоны; граф — только у прогона,
  до пуша ничего.
- **GitLab** — «Pipelines» с мини-графом этапов в каждой строке, а визуализация файла —
  отдельный пункт «Pipeline editor → Visualize», который плохо находят: та же беда, что у нас.
- **GitHub Actions для VS Code** — дерево «workflow → прогоны → задачи → шаги».
- **Blue Ocean, Azure DevOps** — страница прогона: граф сверху, шаги и лог снизу.

Везде пайплайн-файл — запись первого уровня, прогон — его экземпляр. Владелец выбрал по макетам
вариант 1 с мини-графом из варианта 3 и рекомендованные ответы на остальные вопросы.

## Решение

**Две вкладки одной панели** (вариант 1). «Пайплайны» — файлы репозитория, в котором стоит
терминал; «Прогоны» — список ADR 0069 как был. Первой открывается последняя выбранная
(`settings.ciTab`), впервые — «Пайплайны»; где прогоны не читаются (нет программы, нет входа, нет
remote, форж не назван) — тоже «Пайплайны», а над ними строка «почему прогонов нет» с теми же
кнопками, что были у пустого экрана: «Войти в терминале», «Повторить», выбор форжа.

**Пайплайны — из файлов, тем же загрузчиком, что у схемы.** Стор `readPipelines` — `loadGroup` над
`connectionFiles` сессии по корню репозитория: `.github`, `.gitea`, `.forgejo` и `.gitlab-ci.yml`,
с бюджетом и глубиной схемы. Строки — карточки карты (`buildMap`): у GitLab главный файл и дочерние
пайплайны (`trigger: include`), включённые через `include` строками не идут. Вызываемый workflow
назван «вызывается из …». Файлы читаются при нахождении репозитория, по «Обновить» и при возврате
на экран, если прошлое чтение старше минуты, — не по таймеру: они меняются редко.

**Чей прогон** (`ownerOf`): у GitHub — по файлу, который форж называет; у GitLab — главного файла,
кроме дочернего пайплайна (`parent_pipeline`): его файла API не называет, и прогон остаётся ничьим,
а не угаданным. У вызываемого workflow своих прогонов нет — его задачи идут внутри вызвавшего.

**Точки вместо схемы в строке** (из варианта 3). Задачи — точками в колонках схемы (`pipedots.ts`:
этапы GitLab или глубина `needs`, написанные `needs` — линиями); колонка выше четырёх и колонки
после восьмой не рисуются, и сколько не нарисовано — сказано. Цвет — состояния последнего прогона
(`runOnSchema`), серый — пока задачи не прочитаны. Те же точки стоят у каждой строки «Прогонов».
Задачи читаются у последнего прогона каждого пайплайна (`jobsToRead`): закончившегося — один раз,
идущего — с каждым чтением списка, не больше шести за чтение, только пока панель на экране.

**Превью и переходы.** В широкой панели рядом со списком — выбранный пайплайн: что его запускает,
его схема в малом виде (`PipelineGraph` с `compact`: меньше карточки, вызванные задачи свёрнуты до
щелчка) с длительностями последнего прогона, квадраты последних прогонов и «Все прогоны →» — список
прогонов, суженный до этого workflow. В узкой — на месте списка, без превью. Кнопки: «Схема» —
файл на схеме; «Симуляция» — схема с проигранным событием, которое его запускает; «Последний
прогон» — режим «Прогон» на этом прогоне; «Запустить» (есть `workflow_dispatch` или это главный
пайплайн GitLab) — схема на своей форме ручного запуска с курсором в первом поле: своей формы у
панели нет, вопрос перед запуском — прежний. «Карта всех» в шапке — карта группы по корню
репозитория. Просьбы схеме — одной записью стора (`askOnSchema`: прогон, проигрывание, форма),
схема исполняет их, когда пайплайн прочитан.

**⌘K «Схема пайплайнов репозитория»** — карта репозитория, где стоит терминал; не в репозитории —
так и сказано. Пункт меню панели файлов остаётся.

## Не взято

- **Пайплайн — заголовок группы своих прогонов** (вариант 2, как у GitHub). Ломает модель списков
  ADR 0050: при группе «ветка» или без групп пайплайны пропадают; тяжёлые заголовки в узкой панели.
- **Схема прогона целиком в панели** (вариант 3: «Схема | Время | Симуляция» в доке). Рисовала бы
  схему во втором месте рядом с видом в редакторе; из него взяты только точки в строках.
- **«CI» — вид соединения в центре** (вариант 4), панель — лента. Самый дорогой и дублирует вид
  схемы в редакторе.
- **Задачи каждого прогона списка ради его точек.** Тридцать прогонов — тридцать вызовов на
  чтение; точки у прогона без прочитанных задач — форма без цвета.
- **Атрибуция дочерних пайплайнов GitLab по имени задачи-триггера.** Догадка; принцип 5.

## Последствия

- `ci/cipipes.ts` (строки, чей прогон, какие задачи читать, порядок списка), `pipeline/pipedots.ts`
  (точки), `PipelineDots`, `CiPipelines`; `cirun.jobNotes` — общий для схемы и превью;
  `pipelayout.COMPACT`/`compactMetrics` и `foldCalls`.
- Стор `ci`: `readPipelines`, `askOnSchema` (`SchemaAsk`); `editorflow`: `openPipelineSchema`,
  `openRepoPipelines`; настройка `ciTab`; список `ci.pipes` в порядках ADR 0050.
- Гейты: `cipanel.guard` — файлы только через `readPipelines` (загрузчик над `connectionFiles`),
  не по таймеру, задачи точек — только пока панель видна; `listview.guard` — новый список.
