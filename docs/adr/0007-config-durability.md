# ADR 0007 — Атомарная запись конфига и карантин непрочитанного

**Статус:** принято (Фаза 44.1).

## Контекст

Каждый store-файл (`servers.json`, папки, `known_hosts`) перезаписывается **целиком** на
любое изменение. Отсюда два способа потерять данные пользователя штатным путём:

1. Обрыв в момент записи оставлял обрезанный файл — а он декодируется как «серверов нет».
2. Файл, который читается, но не парсится, декодировался в пустой список: UI показывал
   «серверов нет», и следующее сохранение записывало эту пустоту поверх единственной копии.
   Атомарность тут не помогает — ущерб наносит **успешная** запись неверного значения.

## Решение

- **Единственный путь записи — `store::write_atomic`**: temp-сосед → `sync_all` → `rename`.
  Прямой `fs::write` в `store.rs` запрещён. `sync_all` **до** `rename` обязателен: без него
  метаданные могут лечь на диск раньше данных. Ошибку `rename` глушить нельзя.
- **`store::read_store` различает три случая**, и склеивать их нельзя:
  - файла нет — штатный первый запуск, тихий дефолт;
  - файл не парсится — переносится в `<имя>.corrupt-<nanos>` **до** первой записи, копится
    `StoreWarning`;
  - файл прочитан — значение.
- Метка времени в имени карантина — чтобы вторая порча не затёрла улику от первой.
- `quarantined: None` (не удалось даже отодвинуть) — **отдельное** сообщение: «данные спасены
  вот тут» и «данные всё ещё под угрозой» это разные новости. Тост — без TTL.

## Последствия

- Промежуточного состояния файла не бывает: либо старая версия, либо новая.
- Пустой список при первом запуске остаётся тихим — отсутствующий и нечитаемый файл больше не
  путаются.
- Новый store-файл обязан подключаться через `read_store`/`write_atomic`.
- Та же форма применена к `localfile::local_temp` в редакторе: недописанный файл не должен
  быть наблюдаем по настоящему пути.
