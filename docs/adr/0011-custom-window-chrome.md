# ADR 0011 — Своё оконное обрамление на Windows/Linux

**Статус:** принято (v1.0.6).

## Контекст

На Windows системный заголовок окна и **нативная строка меню** (`Файл`/`Справка`)
рисуются ОС и не следуют теме приложения: на тёмной теме верхняя полоса окна
оставалась белой. Заголовок-caption можно перекрасить DWM-атрибутом
(`DWMWA_USE_IMMERSIVE_DARK_MODE`), но **классическая строка меню Win32 не
поддерживает тёмный режим** ни через один публичный API — поэтому приложения с
полностью тёмной рамкой (VS Code, Windows Terminal) не используют нативную строку
меню, а рисуют своё обрамление в WebView.

Рассматривались:

1. **Только DWM-заголовок.** Малый, нативный шаг, но строка меню остаётся светлой —
   результат «полутёмный», разнородный.
2. **Тёмное нативное меню через uxtheme-хаки** (owner-draw, `WM_UAHDRAWMENU`). Грязные
   недокументированные ординалы, хрупкие между сборками Windows — против духа кодовой
   базы.
3. **Свой заголовок + меню в WebView** (безрамочное окно). Полный контроль над видом,
   рамка следует теме; ценой — потеря Snap Layouts и своя реализация ресайза.
4. **Сторонний плагин** (`tauri-plugin-decorum`). Навязывает свой вид и лишнюю
   зависимость — против офлайн/самодельного принципа.

## Решение

Выбран вариант 3 — **безрамочное окно и кастомная рамка на Windows/Linux; macOS
остаётся полностью нативным** (системный заголовок + меню-бар в системной строке).

- Окно создаётся скрытым (`visible:false`); в `setup` на non-macOS снимаются
  декорации (`set_decorations(false)`) **пока окно скрыто** (нет мигания титульной
  рамки), затем `show()` на всех платформах. macOS не трогает декорации в рантайме.
- `build_app_menu` на non-macOS возвращает **пустое** нативное меню — OS-строки меню
  больше нет. macOS-ветка (app-меню «vterm» + Help) без изменений.
- Рамку рисует [TitleBar.svelte](../../src/lib/TitleBar.svelte): логотип, заголовок,
  HTML-меню Файл/Справка (переиспользует общий `ContextMenu`), кнопки
  свернуть/развернуть/закрыть. Сам бар — drag-регион (`data-tauri-drag-region`),
  двойной клик разворачивает окно средствами Tauri.
- Оконные операции идут прямо в Tauri-API окна (`getCurrentWindow()`); права —
  минимальный набор `core:window:allow-*` в capabilities. Декорации снимаются в Rust,
  поэтому `set-decorations` в WebView-права не входит.
- Ресайз безрамочного окна восстановлен своими грип-полосами по краям/углам
  (`startResizeDragging`); геометрия — чистый [windowchrome.ts](../../src/lib/windowchrome.ts)
  (тест `windowchrome.test.ts`).
- Монтирование `TitleBar` и macOS-синк нативного меню гейтятся хостовой ОС через стор
  `hostenv` — на macOS кастомный бар не появляется, на Windows/Linux нативное меню не
  пересобирается.

## Последствия

- Рамка (заголовок + меню + кнопки) целиком следует активной теме — в т.ч. светлым
  темам (кастомный заголовок «прибит» тёмным не был бы честным на Solarized Light).
- **Теряются Windows 11 Snap Layouts** (флайаут при наведении на «развернуть») и
  нативная рамка ресайза — это принятый остаточный минус (грип-полосы заменяют ресайз,
  Snap работает через Win+←/→). Восстановление флайаута потребовало бы `WM_NCHITTEST`
  → `HTMAXBUTTON` субклассинга — отдельное решение, если понадобится.
- **Визуальную проверку рамки нужно делать на реальном Windows/Linux**: на macOS бар не
  монтируется, а frameless-специфика (ресайз, drag, разворот без перекрытия таскбара)
  проявляется только на этих ОС. CI ловит fmt/clippy/test на `windows-latest`, но не
  интерактивное поведение рамки.
- Инвариант «нативное меню строится в Rust» сужен до macOS; правило зафиксировано в
  [INVARIANTS.md](../INVARIANTS.md) (раздел «UI и оформление»).
