# ADR 0047 — Панель файлов под пользователем терминала: дерево процессов и `sftp-server` через sudo

**Статус:** принято (v1.26.0).

## Контекст

`su - deploy` меняет пользователя внутри шелла. SFTP — отдельный канал, вошедший под
пользователем соединения; сервер эти каналы не связывает. Поэтому после `su` панель файлов и
переносы работают под прежним пользователем: копирование падает с `Permission denied` или
создаёт файлы не того владельца, а приложение ничего об этом не знает. Имя в статус-баре —
тоже пользователь соединения: его читает отдельный канал.

Решить надо было две вещи: как узнать, кто сейчас в терминале, и что делать с файлами.

**Как узнать.**

1. *Промпт (`root@host`) или текст команды (`su`).* Промпт у каждого свой, alias и скрипт
   текста команды не показывают, `exit` и Ctrl+D остаются незамеченными. Угадывание — принцип 5.
2. *Сообщение от шелла: добавить пользователя в команду настройки OSC 7.* После `su -` новый
   шелл о ней не знает и молчит. Пришлось бы вписывать её заново — в шелл, который пользователь
   только что открыл.
3. *Дерево процессов на сервере, отдельным каналом.* В терминал ничего не вписывается, виден
   любой способ смены пользователя. Канал и шелл — одно соединение, поэтому шелл — сосед с
   терминалом. Принято.

**Что оказалось на настоящих серверах** (OpenSSH 9.6 и 10, sudo 1.9.15 и 1.9.16):

- *`sudo -i` живёт на другом tty.* С `use_pty` (по умолчанию с sudo 1.9.14) sudo заводит свой
  pty: `bash (pts/0) → sudo (pts/0) → sudo (pts/1) → bash (pts/1)`. Поиск «шелл на нашем tty»
  отвечал бы, что пользователь не менялся. Поэтому передний план спрашивается у каждого
  процесса про **его** терминал (`pgid == tpgid`), а путь идёт по родителям.
- *Разовая команда — не смена пользователя.* `sudo ls` на миг делает передним планом процесс
  root. Ответ — самый вложенный **шелл** на этом пути, а не программа.
- *С `hidepid` не виден даже процесс `sshd`:* запись в `/proc` у него root'овая. Его pid берётся
  из `ppid` соседей; передний план (`tpgid`), которого нет среди видимых, — «другой пользователь,
  кто — сервер скрывает». Это не то же, что «неизвестно»: неизвестное молчит, скрытое сказано.

**Что делать с файлами.**

1. *Только показать расхождение.* Нужно в любом случае, но копировать по-прежнему нельзя.
2. *`sudo cp/mv/tee` на каждую операцию*, как сохранение в редакторе. Второй путь для каждой
   операции; листинг закрытых каталогов и прогресс пришлось бы писать заново.
3. *Запустить `sftp-server` через sudo вместо подсистемы `sftp`.* Тот же протокол поверх того же
   канала, поэтому панель, переносы, редактор и синхронизация остаются как есть. Принято.
4. *`su` вместо sudo.* `su` спрашивает пароль только с tty, значит нужны PTY, сырой режим и
   поиск начала протокола после `Last login`. Отложено: заметно сложнее, отдельным шагом.
5. *Отдельное подключение под этим пользователем.* Работает уже сейчас; вход под root часто
   запрещён. Окно отказа sudo называет этот путь.
6. *Передача через сам терминал (`base64`, `sz`).* Вмешивается в рабочий шелл и историю. Нет.

**Следовать за терминалом сам?** Нет. Файлы, созданные под root, такими и останутся, а
незаметное повышение прав опаснее отказа. Взять пользователя — кнопка и вопрос (на проде
красным), вернуться — только кнопка: это снижение прав.

## Решение

- Зонд `TREE_PROBE` читает `ps`, решает чистая `who`
  ([fileuser.rs](../../src-tauri/src/fileuser.rs)); ответ — `Known`, `Hidden` или `Unknown`.
- Что сказать — чистая `fileUserRow` ([fileuser.ts](../../src/lib/files/fileuser.ts)). Панель
  спрашивает, только пока видима: через секунду после Enter и раз в 15 секунд, потому что `exit`
  по Ctrl+D Enter не шлёт.
- `open_as` сперва спрашивает `sudo … true`: когда `sftp-server` уже запущен, отказ — это просто
  закрытый канал, stderr в поток SFTP не попадает. Затем ищет программу: `Subsystem` из
  `sshd_config`, потом места дистрибутивов. Запускает её в домашнем каталоге цели — `.` панели
  должен быть её, а не закрытый от неё каталог пользователя соединения.
- Пароль идёт только через stdin, строкой перед протоколом: sudo читает его посимвольно до
  перевода строки и отдаёт остальной поток программе. С паролем sudo вызывается с `-k`, иначе
  действующий билет оставил бы пароль непрочитанным — для `sftp-server` это мусор в протоколе.
  Живёт в `Zeroizing` в сессии: он нужен снова для команд ниже.
- Что панель делает не через SFTP (поиск, дерево хэшей, проверка записи), идёт через
  `run_file_command*`/`exec_file_captured` и тоже под этим пользователем: иначе синхронизация
  планировала бы по дереву, которое не смогла прочитать.
- Сессия помнит одно: `SshSession.file_user`. Отказ не меняет ничего; идущее задание держит свою
  `Arc<SftpSession>` и заканчивается как начиналось. Переподключение — новая сессия, значит снова
  пользователь соединения. Смена записывается в аудит (`[sftp] $ as 'deploy'`).

## Последствия

- Опрос — ещё один exec-канал раз в 15 секунд, пока панель на экране, и `ps -A` на сервере.
- Busybox `ps` этих колонок не знает — `Unknown`, панель молчит. То же на Windows-сервере и для
  `su` внутри `tmux`/`screen`: шелл там на другом pty, не в нашем дереве. Вложенный `ssh` и
  `docker exec` остаются пользователем соединения: панель и правда работает здесь.
- Только SSH-вкладки: у локальной нет SFTP, под которым можно работать иначе.
- Без прав sudo взять пользователя нельзя; отказ называет причину. `su` — следующий шаг, если
  понадобится.
- Проверено живыми тестами `live_fileuser` на Ubuntu 24.04 и Debian 13, `hidepid` — вручную в
  привилегированном контейнере. Семейство RHEL не проверялось: `/usr/libexec/openssh/sftp-server`
  есть в списке, но запуска там не было.
