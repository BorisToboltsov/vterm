# ADR 0074 — Несколько логинов у сервера: выбор при подключении, логин у вкладки, секреты у логина

**Статус:** принято (готовится).

## Контекст

Владелец попросил хранить у одного сервера несколько логинов, выбирать один из них при
подключении и назначать логин по умолчанию. Он спросил: «а как выбрать другой?»

Сейчас у профиля один логин: `username`, `auth_method`, `key_path`, секрет в keychain под id
сервера. Чтобы войти под другим логином, сервер приходится дублировать. Тогда расходятся заметки,
теги и флаг прода, а в дереве два одинаковых сервера.

Как это сделано у других:

- **Royal TS** — у подключения одна учётка. «Connect with Options» на одно подключение запрашивает
  другую, профиль не меняется. Вместо имени учётки можно поставить «?» — тогда выбор открывается при
  каждом подключении. Есть шаблоны с другой учёткой.
- **Devolutions RDM** — «Prompt on connection» и «Open with parameters → выбрать учётку».
- **Termius** — логины («Identities») общие для хостов, но у хоста он один. Выбора при подключении
  нет.

Рендеры А–Г с вариантами выбора владелец принял по рекомендации.

## Решение

**1. Логины — у сервера, первый — сам профиль.** `ServerProfile.logins` — остальные логины.
Собственные `username`/`auth_method`/`key_path` профиля — первый логин с id `""`. Сборка, которая
логинов не знает, читает первый и продолжает работать. Ещё два поля:

- `default_login` — логин обычного «Подключиться»; исчезнувший читается как первый;
- `ask_login` — спрашивать логин при каждом подключении.

Id нового логина называет форма (`crypto.randomUUID`), поэтому его секрет сохраняется сразу.
Бэкенд проверяет id (`valid_login_id`) и при слиянии оставляет подсказки keychain за старым id
(`merge_logins`). Отвергнуто:

- общие логины на многих серверах, как в Termius, — это заметно больший объём, оставлено на потом;
- переносить секрет первого логина при смене «главного» — keychain не умеет атомарного
  переименования.

**2. Секреты — у логина.** Область keychain логина — `{сервер}::login::{логин}`, у первого — id
сервера, как и было (`secrets::login_scope`). Пароль входа, passphrase ключа и пароль sudo (ADR
0073) у каждого логина свои. Удалённый логин уносит свои секреты. «Забыть сохранённый пароль»
забывает пароли всех логинов. Отказ сервера во входе забывает пароль только того логина, которым
пробовали войти.

**3. Логин — у вкладки.** `Tab.login` — `{ id }` или `{ once: "user" }`. Вкладка запоминает логин
при открытии, переживает перезапуск (`SavedTab.login` — кто входил, а не секрет), уезжает с ней в
другое окно, и ⌘T открывает вкладку того же логина. Логин, удалённый из профиля, не подменяется
другим: подключение отвечает `login-gone`, а вкладка предлагает выбрать.

Бэкенд помнит логин сессии (`session_logins`). Из него берутся пароли sudo: сохранённый у этого
логина и пароль входа этого логина. У разового логина сохранённого нет.

**4. Как выбрать другой.** Принято: **А + Б + Г**, вариант В отвергнут.

- **А** — меню сервера: «Подключиться» с именем логина по умолчанию справа и подменю «Подключиться
  как» — остальные логины и «Другой логин…». В ⌘K — строки «Подключиться: web как deploy».
- **Б** — быстрый выбор (`LoginPicker`): ⌥↵ и ⌥ + двойной щелчок в дереве, «Другой логин…», а у
  сервера с «Спрашивать» — на каждое подключение. Логины пронумерованы, цифра выбирает сразу, ↑↓ и
  Enter тоже. Звёздочка — логин по умолчанию. «Другой» — пользователь на одно подключение (вход по
  паролю, ничего не сохраняется). Галочка «Добавить в профиль» превращает его в логин сервера
  (`add_server_login`).
- **Г** — экран отказа во входе: рядом с «Ввести пароль» кнопка «Другой логин». Тот же выбор
  подключает эту же вкладку.
- **В** (чип `root ▾` в строке дерева) отвергнут: при каждом наведении он добавлял шум.

Вкладка подписывается `deploy@web-01` только для логина не по умолчанию. Вкладка логина по
умолчанию выглядит, как раньше.

**5. «Открыть как admin».** Если sudo отказал сохранять файл (ADR 0073), в плашке у «Сохранить»
есть кнопки других логинов сервера. Они открывают вкладку под этим логином, и файл переезжает в неё
вместе с правками (`carryEditor`). Файл не перечитывается: сохранение сверяется с версией, на которой
правки начаты, поэтому изменённый тем временем файл даст конфликт, а не тихую перезапись.

**6. Где какой логин.** Логин сессии берут адрес вкладки, строка соединения, контекст ИИ и шапка
записи. Логин по умолчанию берут строка дерева, «Копировать user@host», заметки, выбор целей
рецепта и временный инвентарь Ansible. Прогон рецепта, которому нужна своя сессия, открывает её под
логином по умолчанию и никого не спрашивает. Поиск по дереву и сверка инвентаря с каталогом
смотрят на все логины.

## Последствия

- Второй профиль ради другого пользователя больше не нужен. Заметки, теги и прод у сервера одни.
- Профиль старой сборки читается как сервер с одним логином. Сборка без логинов видит первый.
- Гейт `every_login_reads_its_own_secrets`: `connect_plan` и `connect_session` читают секреты по
  области логина, а не по id сервера; запомнить секрет можно только при наличии области (у разового
  логина её нет).
- Бэкап несёт логины без секретов. Импорт меняет их имена и пути ключей теми же картами. Подсказку
  «пароль сохранён» импорт ставит только логину, который есть в этом keychain (гейт
  `backupimport.guard`).
- Поле секрета нового логина в форме сохраняется после профиля, как и секрет первого.
