# ADR 0035 — Файлы в выводе терминала: каталог берётся в момент отправки строки, ссылкой делает листинг

**Статус:** принято (v1.24.0).

## Контекст

После `ls` или `dir` хочется кликнуть по имени и открыть файл в редакторе — так же, как
из панели файлов, — а папку открыть в панели. Клик в xterm сделать просто: свои ссылки
даёт `registerLinkProvider`, открытие файла уже есть (`openFileInEditor`,
`openLocalFileInEditor`). Трудно другое — понять, **какой файл назван строкой**.

`ls` печатает `nginx.conf`, а не `/etc/nginx/nginx.conf`. Нужен каталог, в котором
выполнилась **эта** команда, а не тот, где шелл стоит сейчас: после `ls` мог быть `cd`.
Ошибка тут — не пустой клик, а другой файл, в том числе на проде.

**Откуда взять каталог строки.**

1. *Текущий каталог шелла в момент клика* (`local_cwd`, OSC 7). Неверен после первого же
   `cd`.
2. *Разобрать промпт.* Промпт у каждого свой; угаданный каталог — правдоподобная
   заглушка (принцип 5).
3. *Запомнить каталог в момент, когда строка ушла в сессию.* Каждая запись с Enter
   проходит через `writeToTerminal` — набор, вставка, синхронный ввод, команда ИИ. Там
   терминал ставит метку xterm («блок» от одного Enter до следующего) и запоминает для
   неё каталог. Принято.

**Каким каталог считать.** Сложность — строка, отправленная не шеллу: внутри вкладки
запущен `ssh` на другой сервер, `python`, `sudo -s`. Каталог шелла ничего не говорит о
том, что такая программа выведет: удалённый `ls -la` в домашнем каталоге совпал бы по
именам (`.bashrc`, `.ssh`) с локальным домашним каталогом.

- *Локальная вкладка.* Бэкенд записывает каталог шелла **до** того, как байты строки
  уходят в PTY (через долю секунды шелл уже выполняет команду или `cd` его сдвинул), и
  только если терминал держит сам шелл. На macOS/Linux это сравнение группы процессов на
  переднем плане (`tcgetpgrp`) с pid шелла, на Windows — нет ли у шелла дочернего
  процесса. Иначе каталог неизвестен. Снимок делается, только пока терминал показывает
  ссылки на файлы (`watch_local_submits`).
- *SSH.* Pid не прочитать. Каталог — последний, о котором шелл сообщил (OSC 7/9;9), и
  только если сообщение пришло **после** прошлой строки: наш сниппет сообщает каталог
  перед каждым промптом, поэтому «сообщения не было» значит «строка ушла не шеллу».
- *PowerShell.* `Set-Location` не меняет каталог процесса, так что снимок ОС устаревает.
  Здесь работает правило SSH, а у `dir`/`Get-ChildItem` есть заголовок `Directory:`.

**Что делает слово ссылкой.**

1. *Разобрать формат `ls`.* Он разный у GNU, BSD и busybox, плюс `-l`, `-F`, цвета,
   кавычки GNU; плюс `dir` и PowerShell. Разбор врал бы на каждом непредусмотренном
   варианте.
2. *Сверить с листингом.* При наведении на строку приложение читает листинг её каталога
   (SFTP или локально — тем же транспортом, что панель файлов) и подчёркивает только
   слова и последовательности слов, совпадающие с именем записи. Принято: ссылкой
   становится то, что проверено.

Команда листинга и её заголовки уточняют каталог строк под собой: `ls /etc` читает имена
в `/etc`, ` Directory of C:\x` и `a:` (`ls a b`) — в названной папке. Это разбор текста
команды, значит угадывание. Поэтому он только сужает, где искать имя, а имя всё равно
должен подтвердить листинг.

**Клик и выделение.** xterm активирует ссылку, если кнопку нажали и отпустили на ней, —
даже когда между этим протянули выделение по имени. Поэтому клик не открывает ничего при
выделении. Первый клик двойного щелчка (выделить слово) ждёт `DOUBLE_CLICK_MS` и
отменяется вторым. В режиме «по ⌘/Ctrl-клику» открытие сразу.

## Решение

- Чистая логика — [termfiles.ts](../../src/lib/termfiles.ts): кандидаты строки, каталоги
  для листинга, подтверждение по листингу, команда листинга, заголовки, имена
  неразмещённого листинга, решение клика. Сторона xterm — блоки, кэш листингов и клик —
  в [filelinkprovider.ts](../../src/lib/filelinkprovider.ts). Страница решает только
  «спросить / открыть / предложить синхронизацию» и открывает по существующим путям:
  файл — редактором сессии, папку — запросом к её панели файлов.
- Вкладка с шеллом контейнера или пода ссылок на файлы не получает (`fileLinksAllowed`):
  её вывод — файлы контейнера, а SFTP сессии читает хост.
- Над SSH-вкладкой, чей шелл каталог не сообщает, имена из листинга — ссылки, которые
  предлагают включить синхронизацию пути (тем же `enablePathSync`, с ответом сервера). Без
  неё имена открыть нельзя, а клик, который молча ничего не делает, — неправда.
- Настройки — «Файлы в выводе» (спрашивать / сразу / не открывать) и «Открывать по»
  (клику / ⌘-клику). Выключено — поставщик ссылок не регистрируется, снимков нет.

## Последствия

- Наведение на строку SSH-вкладки читает листинг её каталога по SFTP — это сеть к серверу
  пользователя по открытой сессии, офлайн цел. Первое наведение открывает SFTP-канал сессии.
- Вывод, напечатанный до включения настройки или до первой команды, ссылок на файлы
  без пути не даёт: каталог для него не запомнен. Абсолютные пути работают везде.
- `cd x && ls` в одной строке читается в каталоге до `cd`. Защита — листинг (имена должны
  совпасть) и вопрос с сервером и полным путём, включённый по умолчанию.
- На Windows проверка «шелл занят» — обход процессов на каждый Enter, пока показываются
  ссылки на файлы. Git Bash печатает пути `/c/...`, которые листинг Windows не подтвердит:
  там работают только короткие имена.
