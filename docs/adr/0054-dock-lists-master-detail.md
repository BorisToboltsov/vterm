# ADR 0054 — Списки Docker и k8s: таблица по ширине списка, подробности — на логе

**Статус:** принято (Готовится, после 1.33).

## Контекст

Нижний док с логами контейнера — самое частое место работы с Docker: лог открыт справа, слева —
список, по которому переходят от контейнера к контейнеру. Вышло неудобно.

- **Имя резалось.** Панель была одним query-контейнером: с подробностями рядом она оставалась
  «широкой», и список половинной ширины держал все четыре колонки фиксированной ширины (имя 200,
  образ 260, статус 150, порты 220 px). Колонки сжимались пропорционально — имя, единственное, что
  отличает строку от строки, урезалось так же, как порты. У подов k8s было то же: три текстовые
  колонки и восемь числовых шириной ~560 px не помещались уже на пороге ширины.
- **Лог — в двух кликах.** Подробности открывались на «Обзоре», лог был второй вкладкой; выбор
  другой строки снова возвращал «Обзор». Логи из меню строки открывались отдельной панелью поверх
  подробностей — у контейнера было два места, где читать его лог.
- **Лог — сплошной текст.** Без фильтра, без уровней, без паузы: чтобы прочитать строку, приходилось
  ловить её между опросами.
- **Не хватало фактов.** Здоровье пряталось в строке статуса (`Up 2 hours (unhealthy)`), счётчика
  перезапусков не было совсем, адреса — нигде. В k8s IP пода не показывался, у ноды — только
  внутренний адрес подписью в «Кластере».

Сравнивали с тем, как это сделано в распространённых инструментах: Docker Desktop (таблица,
страница контейнера с логом первой вкладкой), JetBrains Services и VS Code Container Tools (дерево
имён слева, подробности справа), lazydocker (списки имён слева, большая область лога справа),
Portainer и OrbStack (колонка IP), k9s и Lens (колонки IP и NODE, выбор колонок, подробности сбоку).
Рассматривали пять вариантов: адаптивную таблицу, мастер–деталь, обзор стека, плитки и топологию.

## Решение

**Адаптивная таблица и мастер–деталь вместе.**

- **Список — свой query-контейнер.** Часть со списком носит `@container` и свой `wideWhen`
  (`listWide`): ряды и строка фильтра раскладываются по ширине списка, а не панели. С подробностями
  рядом широкий список становится узким — именем над образом, как в боковом доке.
- **Таблица подгоняется под ширину** (`ui/colfit.ts`, `fitColumns`). Список сам меряет свою ширину;
  колонка, которая не помещается, уходит в заданном порядке (Docker: порты → образ → адрес →
  состояние; k8s: лимиты → график CPU → IP → namespace → нода → память → возраст → перезапуски),
  имя и действия — никогда. Ушедшее названо «+N» с подсказкой. Пользователь может убрать колонку
  сам — «Вид → Колонки», настройка `vterm.columns.hidden`; в «+N» она не считается. Без `-A`
  namespace одинаков во всех строках и уходит первым.
- **Подробности открываются на логе** и при выборе другой строки вид не меняют: список рядом
  просматривают лог за логом. Щелчок по строке открывает подробности; «Логи» и «Инспекция» из
  меню строки — вкладки тех же подробностей, отдельной панелью остаётся только лог стека compose.
- **Лог читается** (`ui/LogTail.svelte`, разбор — `ui/loglines.ts`): «Вживую» / «Пауза», фильтр
  строк, уровень по тексту строки (подсказка, а не разбор формата), 200/1000/5000 строк, время и
  перенос, копирование показанного. Лог по-прежнему снимок, который панель перечитывает, пока за
  ним следят; поток (`logs -f`) открывается в терминале кнопкой.
- **Факты контейнера** — один `docker inspect` на пачку (`inspectFactsArgs`): лимиты, счётчик
  перезапусков, режим сети и адрес в каждой сети, время старта и остановки, код выхода, OOM.
  Переспрашиваются только изменившиеся по `ps` контейнеры (состояние, сети) и работающие раз в
  `FACTS_TTL_MS` (`staleFacts`) — перезапуск по политике `ps` не видит.
- **Адрес — честно.** Адрес контейнера — внутри сети docker; снаружи хоста контейнер доступен через
  опубликованные порты, и подсказка говорит это словами. `host` — «сеть хоста», `none` — «нет сети»,
  `container:X` — сеть X, остановленный — без адреса. В k8s: `status.podIPs` (оба для dual-stack),
  `status.hostIP` рядом с нодой, `hostNetwork` — пометкой; у ноды — InternalIP, ExternalIP, Hostname.
- **«Требует внимания»** над списком (`ui/AttentionStrip.svelte`, модели `dockerAttention`,
  `podAttention`): dead, перезапуск по кругу, OOM, проверка здоровья, выход с ошибкой; у подов —
  CrashLoopBackOff и другие ошибки, Pending и «не готов» дольше своей отсрочки. Перезапуски — только
  выросшие при открытой панели: счётчик, накопленный до неё, — история (как в мониторинге, ADR 0052).
  Выход с кодом 0, 130, 137 без OOM и 143 — остановка по просьбе, не проблема; выход старше суток
  (`FRESH_EXIT_MS`) — история: на живом Docker Desktop полоса иначе держала `exit 255` недельной
  давности от остановленного демона.

## Отвергнуто

- **Дерево имён вместо подвкладок** (как в JetBrains). У «Образов» и «Сетей и томов» свои таблицы,
  фильтры и граф связности; перенос их в дерево — отдельная большая работа. Подвкладки остались,
  мастер–деталь — внутри «Контейнеров» и «Подов».
- **Второй порог ширины для таблицы.** Порог один (`--container-wide`); у списка — свой контейнер
  того же порога, а подгонка колонок — по пикселям, как укладка статус-бара.
- **Плитки** — наглядны на 5–30 контейнерах, бесполезны на сотне и съедают высоту нижнего дока.
- **Топология как основной вид** — отвечает на вопрос «кто кому доступен», а не «что сломалось»;
  остаётся режимом «Сетей» (граф связности Docker, маршрут k8s).
- **Открыть порт в браузере.** Внешние ссылки — только `https://` через opener; опубликованный
  http-порт можно лишь скопировать.

## Дополнено: «Обзор» объясняет контейнер (этап 1)

«Обзор» читает полный `docker inspect <id>` (`parseContainerDetail`) и перечитывает его вместе с
панелью: проверка здоровья с последними запусками и их выводом, команда, политика перезапуска, тома,
окружение, метки. На живом Docker Desktop `unhealthy` у бэкенда объяснялся только выводом проверки
(`HTTP Error 503`, 1200 провалов подряд) — словом состояния это не сказать. Окружение маскируется
шире, чем контекст ИИ (`isSensitiveEnv`: в имени `KEY`, `AUTH`, `SALT`, `DSN`…, в значении — что
находит `redactSecrets`): лишне скрытое стоит щелчка, лишне показанное оказывается на экране
общего звонка. В вопрос ИИ окружение не идёт вовсе; идёт последняя упавшая проверка.

## Дополнено: место и уборка (этап 2)

Сколько занимает docker, читается его же счётом — `docker system df` для сводки и `-v` для того,
кто что использует. Использование образа берётся по id из `-v`, а не сопоставлением имени из `ps`:
контейнер, созданный из `nginx` до нового `pull`, держит старый образ, и имя об этом не скажет.
Обе команды читаются при открытии вида, по «Обновить» и после удаления — на большом хосте `df`
обходит каждый слой, на опросе раз в 3 с ему не место. Несколько контейнеров выбираются чекбоксом
на месте точки состояния (колонки таблицы не сдвигаются), ⌘/Ctrl и Shift-диапазоном; обычный
щелчок по-прежнему открывает подробности. Подтверждение действия над несколькими называет их
по именам, а не по id.

## Дополнено: события и ресурсы (этап 3)

Контейнер с политикой перезапуска, который падает и поднимается между двумя опросами, для `ps`
всегда `running`: счётчик перезапусков растёт, но откуда — не видно, а до того, как панель увидела
рост, — вообще ничего. Это говорят события: `docker events --since 10m --until 0s` проигрывает окно и
завершается — снимок, а не поток, каким `docker events` бывает по умолчанию; политика бэкенда без
`--until` его не пускает. Фильтр берёт только запуски, падения, OOM, kill и смены здоровья: без него
каждая проверка здоровья давала три события `exec_*`. Два падения с ошибкой за окно — круг
(`crashLoop`), он важнее остального и стоит первым. На живом Docker Desktop так нашлись оба
`imaging-worker`, которые список показывал как «running · 30s».

«Ресурсы» не заводят своего опроса: каждый опрос «Контейнеров» уже читает `docker stats`, панель
копит из него ряды всех контейнеров (`pushReadings`, как мониторинг), скорости сети и диска — разность
счётчиков между опросами, счётчик, ушедший назад (перезапуск), — разрыв, а не отрицательная скорость.
Потолок шкалы — только лимит контейнера; без лимита шкала по замерам и подпись «без лимита».

## Дополнено: колонка имён и топология (этап 4)

Дерево разделов вместо подвкладок отвергнуто в начале (у «Образов» и «Сетей» свои таблицы и граф)
и не возвращено: подвкладки остались для полных таблиц, а колонка имён — список, ставший узким рядом
с подробностями, — продолжается разделами образов, сетей и томов. Так из одной колонки выбирается
что угодно, а полные виды на месте. Кто использует образ или том, спрашивается у docker фильтром
(`ps --filter ancestor=<id>`, `--filter volume=`), не сопоставлением имён. Граф «Сетей» стал
топологией: слева опубликованные порты хоста (кто их достигает — цветом), в середине контейнеры с
адресами из фактов (этап 0), справа сети с подсетями — одним `network inspect` на все сети,
переспрашиваемым только при смене их набора. Без опубликованных портов колонок две.

## Дополнено: compose (этап 5)

Из чего стек, говорят метки его контейнеров: каталог, файлы и env-файл, с которыми он поднят. На
живом стеке `life-e2e` (два файла и свой `e2e.env`) `compose config` по одному каталогу падал на
незаданной переменной — определение стека живёт в его файлах, а не в каталоге. Поэтому
конфигурация и список сервисов читаются с `-f` и `--env-file` из меток, и политика бэкенда пускает
их только для `config`, который ничего не запускает (прочитать файл приложение и так может панелью
файлов). Всё, что запускает, файлов не называет: `start`/`stop`/`restart` сервиса идут по имени
проекта, а `up` — из каталога, и потому предлагается, только где стек поднят из файлов по умолчанию
этого каталога (`usesOwnFiles`); иначе панель даёт скопировать команду с файлами стека для
терминала — то же правило отключает «Поднять» в заголовке такого стека.

Найденный по ходу риск закрыт там же. Политика argv не может знать, чей каталог назван, — путь есть
путь, — поэтому `container_run` перед compose с `--project-directory`, `-f` или `--env-file` тем же
транспортом спрашивает метки контейнеров проекта (`stack_labels_args`) и пускает только каталог, из
которого стек поднят, и его файлы (`check_stack`); проект без контейнеров — отказ: сверить не с
чем. Лишний вызов `docker ps` — только у таких команд, опрос его не платит.

## Дополнено: «Обзор» объясняет под (k8s, этап 1)

У пода всё нужное уже лежит в `get pods -o json`, который список опрашивает: «Обзор» разбирает объект
открытого пода из того же ответа (`parsePodDetail`), своего вызова у него нет, и он обновляется с
опросом. Условия пода — по порядку подъёма, с их собственными словами: почему под в `Pending`,
говорит `PodScheduled` («0/1 nodes are available: 1 Insufficient memory»). Каждый контейнер —
приложения, затем нативные сайдкары, затем отработавшие init — с состоянием, сообщением kubelet и
**прошлым завершением**: `CrashLoopBackOff` прячет причину, а `lastState` её хранит (`OOMKilled`,
код 137). Пробы — что делают и как часто, запросы и лимиты, тома с их источником. Окружение — тем же
правилом, что у Docker (`isSensitiveEnv` переехал в `ai/redact.ts`); значение из Secret не читается
вовсе — показано только, откуда оно. У завершённого пода `Ready=False` — следствие конца, а не
поломка: условия серые (`finished`). В вопрос ИИ идут несработавшие условия и то, как кончились
контейнеры (`podDetailFacts`); окружение — ни значениями, ни именами. Всё сверено на стенде
`e2e/k8s` (k8s 1.31.1): у каждого пода с поломкой «Обзор» называет её причину.

## Дополнено: события пода и причины «Требует внимания» (k8s, этап 2)

События спрашиваются только у открытого пода — по его uid (`podEventsArgs`: под, пересозданный под
тем же именем, — другой под), пока на экране «Обзор», и с каждым опросом. На опросе списка событий
нет: на большом кластере `get events` по всему namespace — тысячи объектов каждые пять секунд ради
полосы, которой хватает самого пода. Поэтому причины «Требует внимания» читаются из объекта пода
(`podSigns`): убит за память (`OOMKilled` в состоянии или `lastState`, не старше часа —
`RECENT_OOM_MS`, дольше контейнер помнит старое убийство), образ не скачивается, планировщик не
нашёл ноду (`PodScheduled=False/Unschedulable`, его слова без хвоста про вытеснение —
`schedulerReason`), не проходит проба готовности (неготовый работающий контейнер, у которого она
есть). Проба живости так не видна: убитый ею контейнер — просто `Error 137`, а причина — только в
событии `Unhealthy`; поэтому её говорит «Обзор», а не полоса. На стенде у пода с проваленной пробой
живости событий `Unhealthy` не оказалось вовсе — kubelet отбрасывает частые события одного объекта,
и «Обзор» об этом предупреждает. Там же нашлась ошибка разбора: планировщик пишет повторы в
`series` (`count`, `lastObservedTime`) без `count` и `lastTimestamp`, и «Кластер» показывал ×1 и
время первого раза; теперь читается `series`.

## Дополнено: ресурсы пода (k8s, этап 3)

«Ресурсы» не заводят своего опроса для пода: `top pods` уже идёт с каждым опросом списка, и панель
копит из него CPU и память каждого пода (`podReadings` → `pushReadings`), — вкладка открывается с
тем, что намерено, пока она была закрыта. Контейнеры открытого пода (`top pod --containers`)
спрашиваются, только пока вкладка на экране: каждый — против своего лимита, потому что OOM убивает
контейнер, упёршийся в свой, что бы ни говорила сумма пода. Потолок графика пода — лимит запущенных
контейнеров (приложения и сайдкары; без лимита у одного — без потолка, шкала по замерам), запрос —
отметка (`threshold`), а не потолок: под может брать больше запрошенного. Сети и диска metrics API не
сообщает — так и написано, нулём не рисуется. Почему замеров нет, различается (`metricsGap`): в
кластере нет metrics-server (как в Docker Desktop — потолки из описания пода всё равно показаны),
замеров ещё нет (он меряет раз в 15–60 с, у неработающего пода их не бывает), другой отказ — его
словами. На metrics-server 0.9.1 под без замера отвечает `NotFound` (`pods "x" not found`, хотя под
есть) — это «ещё нет», а не отказ. `kubectl top` округляет память до MiB, поэтому ноль остаётся `0Mi`,
а не «0Ki», которых в ответе нет. Шкала без лимита вмещает запрос: под, берущий 2m при запросе 15m,
иначе прятал отметку над шкалой.

## Дополнено: подробности нагрузок (k8s, этап 4)

Нагрузка открывается щелчком, как под: рядом со списком в широкой панели, окном в узкой
(`K8sWorkloadDetail` + тонкий `K8sWorkloadModal`); одна подробность за раз — открытая нагрузка
убирает под, под — нагрузку. Что ей велено, что у неё есть и что она о себе говорит, читается из
опроса «Нагрузок» (`parseWorkloadDetail`), своего вызова нет: реплики, стратегия, ревизия и срок
выкатки, условия (`ProgressDeadlineExceeded` со словами контроллера), образы; у StatefulSet —
ревизии и заявки на тома, у DaemonSet — поды не на своих нодах, у CronJob — расписание, последний
запуск и последний успех («ни разу» — тоже ответ). Что ей принадлежит, спрашивается только у
открытой и только пока «Обзор» на экране — её поды и ReplicaSet'ы Deployment, по её селектору
(`selectorArg` → `--selector`), а берутся по владельцу (`workloadPods`, `parseRevisions`): селектор
может совпасть и с чужими. Ревизии — ReplicaSet'ы по `deployment.kubernetes.io/revision`, текущая
отмечена; на стенде `rollout` после `set image` на несуществующий образ — ревизия #2 «0/1» при #1
«2/2»: выкатка, застрявшая на полпути, видна сразу.

Job'ы приходят тем же опросом «Нагрузок» (`deployments,…,cronjobs,jobs`): свой Job — строка списка,
запуск CronJob — в подробностях своего CronJob с итогом и причиной (`BackoffLimitExceeded`). Они же
снимают долг этапа 0: под запуска CronJob принадлежит Job'у, чьё имя — «report-29901014», и
«Поды» собирали каждый запуск в свою группу. Теперь поды Job'ов сворачиваются к CronJob по
`ownerReferences` самих Job'ов (`jobOwners`), а `get jobs` на опросе «Подов» идёт, только когда
такие поды есть; по имени Job'а владелец не угадывается.

## Последствия
