# ADR 0069 — Прогоны CI: панель, прогон на схеме, аудит workflow — через gh и glab пользователя

**Статус:** принято (готовится).

## Контекст

ADR 0068 дал схему пайплайна по файлу: что запустится при событии, до пуша. Чего не было — что
было на самом деле: прогоны, их задачи и шаги, лог упавшего шага, перезапуск, ручной запуск.
ADR 0068 отложил это (решение 2г) как новое сетевое исключение под отдельный ADR.

Сравнили, кто так умеет:

- **GitHub в вебе** — список прогонов, граф задач с длительностями, лог, перезапуск, ручной запуск.
  Критического пути не показывает, до пуша ничего не знает.
- **GitHub Actions для VS Code** — прогоны workflow и ветки, логи, перезапуск, `workflow_dispatch`,
  подсказки при правке файла. Только локально, только GitHub.
- **GitLab Workflow для VS Code** — статус пайплайна ветки, задачи, логи, повтор и отмена, проверка
  конфига. Только GitLab.
- **zizmor** — статический аудит безопасности workflow; часть проверок без сети, часть ходит в API.
- **act**, **gitlab-ci-local** — прогон локально в Docker.

Пустое место: прогоны обоих форжей там, где работает человек — на сервере за SSH тоже, —
нарисованные той же схемой, что симуляция, с настоящим временем. Владелец выбрал рекомендованные
решения по макетам (прогон на схеме, панель «CI», значки в истории Git, аудит и форма запуска).

## Решение

**Сеть — программами пользователя.** Панель зовёт `gh api` и `glab api` — те программы, которыми
человек пушит, на хосте сессии (принцип 3), под его входом. Приложение сокетов не открывает и
токенов не видит: трафик делают процессы пользователя, как `curl` в HTTP-клиенте (ADR 0014).
Без программы — «gh не установлен здесь» (`exit 127`), без входа — «gh не вошёл» и кнопка, которая
печатает `gh auth login` в терминал вкладки. `gh`/`glab` добавлены в «Серверные инструменты».

**Только REST, только пути прогонов** (`ci::check_args`). `gh api` целиком достаёт до любого
эндпоинта токена — удаление репозитория один вызов, — поэтому политика пускает список прогонов,
прогон, его задачи, лог задачи, список workflow, коммит действия (для закрепления по SHA) и четыре
записи: перезапустить упавшие, перезапустить всё, отменить, запустить вручную (`dispatches` GitHub,
`pipeline` GitLab). Запись пишется явно (`-X POST`): поле, добавленное к чтению, не превратит его в
запись. Ни одной опции, читающей файл (`--input`, `-F key=@path`): `-F` пускается только как
JSON-массив переменных пайплайна GitLab. Хост, сегменты пути и значения запроса — по алфавиту.
Отвергнуто: высокоуровневые `gh run`/`glab ci` — у `glab` нет стабильного JSON на всё, и два набора
форм держать дороже одного REST.

**Где живёт.** Панель дока «CI» (нижний док, скрываемая): список прогонов репозитория, в котором
стоит терминал (`gitCwd`), — фильтр, группы и порядок ADR 0050; рядом в широкой панели и вместо
списка в узкой — прогон: что можно сделать, задачи (у GitHub — шаги), хвост лога открытой задачи с
отмеченными строками ошибок, «Весь лог» — документ только для чтения, «Спросить ИИ» — через
маскирование и согласие (`askAbout`, источник `ci`), «К строке» — если путь из лога есть в HEAD.
Несколько remote — выбор в шапке; хост, имя которого не говорит, чей он (GitLab на LAN-адресе), —
вопрос один раз, ответ в `settings.ciForges`.

**Когда читает.** Пока панель на экране: раз в 10 с, пока что-то идёт, иначе раз в минуту; возврат
на экран — одно чтение сразу. Исключение одно и явное — «Следить» у идущего прогона: стор спрашивает
этот прогон раз в 15 с при скрытой панели и говорит в журнал, чем он кончился; слежка кончается с
прогоном, с отказом форжа и с вкладкой (`forgetCi`). Значки CI в истории Git — из последнего списка
стора; Git читает его заново со своей историей, не чаще раза в минуту, своего цикла у него нет.

**Прогон на схеме.** В виде файла — «Симуляция | Прогон»; «Прогон» берёт прогоны этого файла,
схему — из файла на коммите прогона (`git show sha:path` на хосте сессии, через стор); коммита нет —
текущий файл, и так и сказано. API не отдаёт связей задач, поэтому задача прогона ставится на задачу
файла по имени, которое даёт форж: копия матрицы GitHub — `name (v1, v2)` по порядку ключей,
пустые значения выпадают, или шаблон `name:` со значениями матрицы; задача вызванного workflow —
`вызвавший / задача`; GitLab — `job 1/3` и `job: [a, b]`. Неизвестное выражение в имени — шаблон,
а не догадка; что не встало ни на одну задачу, названо. «Порядок» — граф с настоящими состояниями и
длительностями на карточках; «Время» — строка на задачу, ожидание раннера (`created_at` →
`started_at`) пунктиром, критический путь подсвечен: от закончившейся последней — назад через то,
что закончилось последним до её создания (задачу создают, когда кончилось то, чего она ждёт), среди
её `needs`, если они известны. Проигрывание — по собственным временам прогона, ускоренно.

**Безопасность workflow — без сети.** Шесть проверок по файлу (подмножество zizmor):
`pull_request_target`/`workflow_run` с checkout головы PR, подстановка текста, который пишет кто
угодно, в `run:` и `github-script`, действия по тегу вместо SHA, нет `permissions:`, `write-all`,
`secrets: inherit`, `persist-credentials`. Это предохранитель (принцип 7): лучше лишнее слово, чем
пропуск. «Закрепить по SHA» — по кнопке: коммит тега спрашивается у github.com через `gh`, правка
файла — одна, одной отменой.

**Ручной запуск** — форма, которую описывает файл: `workflow_dispatch.inputs` (типы, варианты,
обязательность) или переменные GitLab с `description:`. Вопрос перед запуском называет значения;
значение `production` — красным. В диагностику — сколько полей, не значения; в запись — имена.

## Не взято

- **Запуск локально через `act` и `gitlab-ci-local`** — следующий шаг; команда в терминал.
- **Автодополнение `${{ … }}` и подсказки** при правке workflow.
- **`paths:`/`changes:` из diff** для симуляции (решение 2в ADR 0068).
- **ИИ «объясни пайплайн»** (решение 7 ADR 0068).
- **Свои сетевые вызовы к API форжей** — токены пришлось бы хранить и переносить; у пользователя
  уже есть вошедший CLI.
- **Шаги задач GitLab** — их нет в API: задача без шагов, лог целиком.

## Последствия

- Подсистема `src/lib/ci/`: `forge.ts` (remote → форж), `ciapi.ts` (argv), `ciparse.ts` (ответы,
  лог, отказы), `cirun.ts` (задачи на схеме, время, критический путь), `ciaudit.ts`, `cidispatch.ts`,
  `citext.ts`; компоненты `CiPanel`, `CiRunDetail`; `PipelineTimeline` в `pipeline/`.
- Стор `stores/ci.svelte.ts` — единственный, кто зовёт `ciRun` (правило `owned-imports`): чтения,
  записи с аудитом `[ci]`, кэш для значков Git, слежка, вопрос схемы о прогоне.
- Rust: `ci.rs` (политика, окружение без подсказок и пейджера), команда `ci_run` в мосте драйверов;
  `git remote -v` в политике Git; источник диагностики `ci`.
- Гейты: `cipanel.guard`, Rust `what_the_ci_panel_runs_is_allowed`,
  `the_ci_panel_reaches_only_the_runs_of_a_repository`; панель — в `dockpanels.guard`,
  `listview.guard`, снос — в `tabteardown.guard`.
