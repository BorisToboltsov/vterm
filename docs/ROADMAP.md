## 🔁 Принцип сборки: два файла на каждом этапе

Один файл, работающий и на Windows, и на macOS, **невозможен** (разные форматы
исполняемых файлов). Поэтому **на каждой фазе собираются два артефакта**:

- **macOS** — `.app` (портативный бандл) + `.dmg`;
- **Windows** — `.msi` / NSIS `.exe` (+ портативный `vterm.exe`).

**Definition of Done каждой фазы** включает зелёную CI-сборку обеих ОС. Механизм —
**GitLab CI** [.gitlab-ci.yml](../.gitlab-ci.yml) (задачи `build:macos` + `build:windows`):
push в дефолтную ветку/MR/ручной запуск → артефакты пайплайна; push тега `v*` →
GitLab Release для обеих ОС.

> Локально доступна сборка только под текущую ОС (`pnpm tauri build`). Windows-файл
> на macOS не собрать — для него нужен Windows-раннер из CI.

## ✅ Фаза 17 — ИИ-агент (opt-in)

**Цель:** встроить ИИ-ассистента для работы с серверами — чат, исполнение команд с
подтверждением, генерация планов и скриптов из записей сессий. **Полностью opt-in,
выключен по умолчанию.**

**Зафиксированные решения (обсуждено 2026-06-30):**
- **Офлайн-инвариант — осознанно ослаблен:** ИИ выключен по умолчанию; **весь
  LLM-трафик идёт через Rust-бэкенд** (`reqwest`), не из WebView, поэтому CSP остаётся
  строгим, а фронт-гейт `autonomy.guard` — зелёным; разрешены **только пользовательские
  эндпоинты** (нет зашитых облаков/телеметрии) — «как SSH». Обновляются `autonomy.guard`,
  [SECURITY.md](../SECURITY.md), [INVARIANTS.md](INVARIANTS.md).
- **Провайдеры:** адаптер **OpenAI-совместимый** (`/v1/chat/completions` — Ollama/vLLM/
  LM Studio/локальный Qwen/OpenAI) **+ Anthropic** (нативный Claude) с самого начала.
  Конфиг эндпоинта: тип/baseURL/модель/ключ (keychain `vterm:ai-key`, `zeroize`); несколько
  эндпоинтов с выбором активного.
- **Исполнение:** *только предложить* / **подтверждать каждую** (дефолт) / *опц. авто* —
  авто-режим разрешён **только на не-прод** серверах под явным флагом; на проде — никогда.
- **Приватность:** перед отправкой — маскирование секретов + окно явного согласия
  «отправить N строк на `<endpoint>`» (и для локальных, и для облачных эндпоинтов).
- **Модель контекста — manual-first по уровням:** по умолчанию ИИ видит **выделение /
  последние N строк**; «приложить весь буфер», «приложить запись», «приложить метаданные»
  (ОС/hostname/ядро) — **явными переключателями**, всё через маскирование + согласие.
- **Контракт вывода — переключаемый в настройках:** v1 **Markdown-парсинг** (```bash → кнопка
  «Выполнить»; дефолт, модель-агностично, работает на слабом локальном Qwen) **и** v2 **нативный
  tool-calling** (`run_command()`, для моделей с function-calling). Выбор — в настройках ИИ.
- **MCP — отложен:** нативного tool-calling в брокере достаточно для старта; MCP добавляем
  позже ради экосистемы внешних инструментов (опционально).

## Заметки по архитектурным решениям

- **`portable-pty` — для локального терминала.** SSH-вкладки используют удалённый
  PTY канала `russh` напрямую; для **локальной shell-вкладки** («+» в списке
  вкладок) добавлен `portable-pty` (forkpty на Unix, ConPTY на Windows) —
  [pty.rs](../src-tauri/src/pty.rs). Локальный PTY переиспользует те же события
  `term://out|closed/{id}` и команды `write_to_terminal`/`resize_pty`/`disconnect`,
  что и SSH, поэтому фронтенд-виджет терминала общий.
- **`russh-keys`** в свежих версиях влит в `russh` — проверить актуальность на момент
  начала Фазы 2.
- **`keyring` vs собственное шифрование** — основным выбран `keyring` (системное
  хранилище). `chacha20poly1305` под мастер-пароль — опция для портативного файла.
- **Хранение профилей** — простой JSON-файл на стороне Rust (`serde` + `directories`),
  без `tauri-plugin-store` (это фронтовое хранилище настроек, дублирование не нужно).
- **Tailwind v4** вместо 3.x из исходного плана — интеграция одним плагином Vite,
  без `tailwind.config.js`/PostCSS.
