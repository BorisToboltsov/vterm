# Security

Документ описывает модель безопасности vterm, автоматические проверки (SAST /
supply-chain) и принятые исключения. Часть Фазы 6.1 дорожной карты.

## Что делает приложение

vterm — локальный SSH/SFTP-клиент. Он **офлайн по умолчанию**, кроме исходящих SSH к
серверам, которые добавил пользователь (см.
[«Сеть и автономность»](README.md#сеть-и-автономность) и ADR
[0004](docs/adr/0004-offline-first.md)). **Опционально** (Фаза 17, выключено по
умолчанию) можно включить ИИ-ассистента: тогда добавляется исходящий трафик к
**пользовательскому** LLM-эндпоинту (локальный Qwen/Ollama или облачный Claude по
выбору пользователя). Весь LLM-трафик идёт из Rust-бэкенда (`src-tauri/src/ai.rs`,
`reqwest`), не из WebView — CSP остаётся строгим, фронтенд сетевых вызовов не делает;
зашитых облачных эндпоинтов нет, ключи API — только в keychain (`vterm:ai-key`).
Ещё одно исключение — «Проверка доступа» на локальной вкладке: TCP-рукопожатие к адресам,
которые пользователь ввёл сам, только по кнопке, — или, по его выбору, его же
`bash`/`nc`/`telnet`/`curl` к тем же адресам ([ADR 0012](docs/adr/0012-local-access-check.md),
[ADR 0032](docs/adr/0032-access-check-requests.md),
[ADR 0033](docs/adr/0033-access-check-picked-servers-local-tools.md)),
и TLS-инспектор/HTTP-клиент на локальной вкладке — они запускают **свои** `curl`/`openssl`
пользователя на этот адрес, тоже только по кнопке ([ADR 0014](docs/adr/0014-local-tls-http-probes.md)).
Контекст сессии прикладывается к запросу **только по явному действию пользователя**, проходит
**маскирование секретов** (`redact.ts`, маркер `‹redacted›`) и **окно согласия** с
предпросмотром перед отправкой — в том числе на локальный эндпоинт. Секреты хранятся только
в системном keychain; ничего не отправляется во внешние сервисы.

## Автоматические проверки (CI-гейты)

Проверки разделены на **блокирующие** и **советующие**, и это разделение осознанное:
политика с расписанными исключениями обязана ронять прогон, иначе она не политика;
сканер с правилами из внешнего реестра ронять чужой PR не должен — иначе его отключат
целиком. Раскладка по workflow — в [docs/TESTS.md](docs/TESTS.md#ci-на-github).

**Блокирующие** — [ci.yml](.github/workflows/ci.yml), джоба `deps`:

| Проверка | Инструмент | Что ищет |
|----------|-----------|----------|
| Rust advisories и политика | `cargo deny check` | RUSTSEC (уязвимости, unmaintained, yanked) + лицензии + дубликаты + источники |
| JS advisories | `pnpm audit` | уязвимости npm-зависимостей |

Принятые advisory расписаны с причинами в [deny.toml](src-tauri/deny.toml) — это единственный
их список: `cargo audit` читал ту же базу RustSec, но держал второй список исключений и не умел
падать на устаревшем, поэтому с 1.25.5 его нет. Для npm аналогичного списка пока нет — база чистая; появится
advisory без апстрим-фикса, исключение заводится через `auditConfig.ignoreCves` в
[pnpm-workspace.yaml](pnpm-workspace.yaml), с причиной рядом. Снимать блокировку молча
нельзя.

**Советующие** — находки едут в **Security tab** формате SARIF (дедуп, история,
аннотации в диффе PR), а не в лог, который никто не читает:

| Проверка | Инструмент | Что ищет |
|----------|-----------|----------|
| SAST — весь код | **CodeQL** (`javascript-typescript`; `rust` — на `main` и ежемесячно, базу строит полная сборка) | поток данных, инъекции, небезопасные API |
| SAST — сами workflow | **CodeQL** (`actions`) + **zizmor** | подстановка `${{ }}` в `run:`, незапиненные экшены, лишние права токена |
| SAST — анти-паттерны | **Semgrep** (`p/typescript`, `p/javascript`, `p/rust` без `unsafe-usage`) | анти-паттерны фронтенда и бэкенда; находка, разобранная на месте, — `// nosemgrep` с причиной над ней |
| ФС | **Trivy** (`fs`: secret/misconfig) | секреты, misconfig |

У каждой заботы один сканер: уязвимости зависимостей — только `cargo deny` и `pnpm audit`
(Trivy `vuln` читал те же lockfile без их исключений), секреты — только Trivy (`p/secrets`
Semgrep давал вторую копию находки), `unsafe` — только clippy `undocumented_unsafe_blocks`,
жёстко: у каждого блока `// SAFETY:` (правило Semgrep `unsafe-usage` помечало каждый блок
подряд, с обоснованием или без). Держит гейт `ci.guard.test.ts`.

**Фаззинг недоверенного входа** — [deep.yml](.github/workflows/deep.yml). У vterm
нет ни одного HTTP-порта, поэтому DAST здесь нечего сканировать; динамическая поверхность
— это парсеры, которым подают чужие байты (markdown из ответа LLM, `.md` по SFTP, вывод
скомпрометированного хоста, кодировки файлов). Проверяются свойствами на произвольном
входе: из рендера markdown не выходит исполняемого ни при каком вводе, декодер не паникует
на произвольных байтах. Подробности — [docs/TESTS.md](docs/TESTS.md#фаззинг-недоверенного-входа).

### Цепочка поставки CI

- **Экшены запинены по коммит-SHA**, а не по тегу: тег изменяем, и его владелец может
  переписать содержимое в любой момент — а `tauri-action` получает токен на запись
  в публикуемый релиз. Пин без обновления консервировал бы уязвимость, поэтому его
  двигает Dependabot ([dependabot.yml](.github/dependabot.yml)), с **выдержкой `cooldown`
  7 дней** — скомпрометированный релиз апстрим обычно отзывает в первые дни. Наличие пина
  и комментария версии держит гейт `releaseassets.guard.test.ts`.
  - **Пинить нужно КОММИТ, а не объект аннотированного тега.** У аннотированного тега
    (например `rust-cache@v2.9.1`, `codeql-action@v4.37.3`) две разные хэш-величины: объект
    тега и коммит, на который он указывает; `git ls-remote` без разыменования `^{}` отдаёт
    первый. Пин на объект тега формально иммутабелен, но не совпадает с тем, что резолвит
    версию из комментария, — и это законно ловит zizmor (`ref-version-mismatch`). Правильный
    SHA — `git ls-remote --tags <repo> | awk '$2==\"refs/tags/<ver>^{}\"'`.
  - **Комментарий версии обязан совпадать с тем, куда тег указывает СЕЙЧАС.** У плавающего
    тега (так было с `dtolnay/rust-toolchain@v1`, пока Rust ставил он) SHA из старого PR Dependabot остаётся на линии тега, но
    `# v1` рядом с ним уже ложь — zizmor (`ref-version-mismatch`) это ловит. Перепиннивая, бери
    текущий SHA тега, а не SHA из PR.
- **Свои workflow и экшены — через `$/…`, а не `./…`** (синтаксис self-repository, GitHub с
  07.2026). `./…` резолвится по рабочему каталогу раннера в момент запуска, и шаг, склонировавший
  туда что-то раньше, подменил бы экшен; `$/…` привязан к коммиту и считается пином для политики
  «fully pinned». Держит `releaseassets.guard.test.ts`.
- **Каждый checkout — с `persist-credentials: false`**: иначе `GITHUB_TOKEN` оседает в
  `.git/config` и доступен любому последующему шагу (zizmor `artipacked`). Ни один наш шаг не
  пушит через git — релизы идут через API, кредам в рабочей копии делать нечего.
- **Права токена выдаются поджобно, а не на весь workflow**: верхний уровень — `contents: read`,
  запись просят только джобы `release`/`integrity` (zizmor `excessive-permissions`).
- **В публикующем `release.yml` нет кэша**: кэш в workflow, который публикует, — вектор
  отравления (недоверенный PR пишет в кэш-ключ, релизная сборка его восстанавливает; zizmor
  `cache-poisoning`). Релиз редок и собирается из чистого состояния — те байты мы подписываем
  provenance. Кэш остаётся в `ci.yml`/`deep.yml`, где публикации нет; общие экшены
  `.github/actions/` кэшируют только по просьбе джобы, и `release.yml` не просит
  (`ci.guard.test.ts`).
- **Общие шаги — один экшен на всех, версия Rust — одна.** pnpm, Node, Rust, пакеты Tauri и кэш
  ставят только `setup-web`/`setup-rust` в `.github/actions/`: пин, поднятый в одной копии шага
  и забытый в другой, больше негде оставить. Rust — версия из `rust-toolchain.toml`, а не
  «`stable` сегодня»: сборка релиза воспроизводима тем же компилятором, что прошёл гейты.
- **Имя тега уезжает в шаг через `env`**, а не подстановкой `${{ github.ref_name }}` прямо
  в `run:`: подстановка происходит **до** запуска шелла, то есть значение становится кодом.
  Создать тег может только тот, у кого есть push, но класс уязвимости от этого не меняется.
- **Релиз не собирается из красного дерева**: тег запускает полный набор гейтов
  (`workflow_call` в `ci.yml`), и матрица сборки стоит под `needs`.

### Целостность релиза

Сборки не подписаны Developer ID и подписываться не будут (принятый риск: фаза 16 в
[ROADMAP](docs/ROADMAP.md) закрыта без реализации), а INSTALL.md прямо учит получателя снимать
карантин Gatekeeper. Поэтому к каждому релизу прикладывается то, чем он может проверить файл сам:
`SHA256SUMS`, **SLSA-provenance** (`actions/attest-build-provenance`, проверяется
`gh attestation verify`) и SBOM в CycloneDX. Provenance подпись **не заменяет** — он
отвечает на другой вопрос, «те ли это байты, что вышли из сборки этого репозитория».

**Отправка ассетов во VirusTotal — opt-in.** Неподписанный portable `.exe` — классический
кандидат в *ложные* срабатывания SmartScreen и эвристик, и знать об этом надо раньше
пользователя. Задача обратная той, что кажется: мы не ищем вирус в бинаре, который сами
скомпилировали. Но это отправка артефакта третьей стороне, поэтому шаг включается только
тем, что владелец репозитория завёл секрет `VT_API_KEY`; без него наружу не уходит ничего.
Условие закреплено гейтом.

**Вшитый WebView2 в «полном» portable** (ADR 0013). `vterm-portable-*-x86_64-webview2.exe`
несёт `.cab` WebView2 Fixed Version runtime. CI берёт его со страницы Microsoft, принимает
только с хоста `msedge.sf.dl.delivery.mp.microsoft.com` и **вшивает только при валидной
подписи Authenticode Microsoft Corporation**. При распаковке vterm сверяет sha256 из хвоста
exe, а имя каталога версии разбирается строго (четыре числа), чтобы повреждённый хвост
не увёл распаковку за пределы кэша. **Принятый риск:** вшитый движок не обновляется, его
свежесть привязана к релизам vterm. Поэтому системный WebView2, если он есть, побеждает
вшитый всегда, а вшитый — только для машин, где иначе не запустилось бы ничего.

Конфигурации без DOM-зависимостей дополнительно защищены **юнит-гейтами** (падают
в обычном `pnpm test`):

- `src/lib/ai/autonomy.guard.test.ts` — нет runtime-обращений в сеть;
- `src/lib/repo/tauri-security.guard.test.ts` — CSP задан и строгий, capabilities —
  минимально необходимые, opener ограничен `https://`;
- правило линтера `vterm/md-links` ([lint/vterm.js](lint/vterm.js)) — каждый показ markdown
  защищён обеими половинами ссылочной защиты (см. «Недоверенный markdown» ниже);
- правило линтера `vterm/no-network` — из WebView нет `fetch`/`XMLHttpRequest`/`WebSocket`/
  `EventSource`/`sendBeacon`, `vterm/invoke-in-api` — бэкенд зовут только обёртки `src/lib/api`;
- `src/lib/repo/releaseassets.guard.test.ts` — цепочка поставки CI: пиннинг экшенов по SHA,
  релиз под гейтом, материал целостности в ассетах, opt-in VirusTotal.

### Триаж внешнего SCA/SAST-скана (2026-08)

Прогон стороннего сканера (SCA по локфайлам + SAST по коду). Внешний инструмент не
видит [deny.toml](src-tauri/deny.toml)/`pnpm-workspace.yaml`, поэтому в его отчёт попадает
и уже принятое по политике, и dev-инструменты, и то, что чинится апстримом. Итог триажа:

**Зависимости — исправлено апстрим-фиксом:**

- `russh 0.61.2 → 0.62.5` — закрывает четыре advisory (GHSA-5xvq-cp9x-6p6r,
  GHSA-g9hv-x236-4qp3, GHSA-cqjc-rmpq-xprq, CVE-2026-68930). Прямая зависимость, SSH — ядро.
  Потянул `ssh-key =0.7.0-rc.10 → =0.7.0-rc.11` (russh его переэкспортирует — пин обязан
  совпадать, чтобы Cargo сводил к одной копии); ряд RustCrypto-крейтов при этом ушёл с rc на
  стабильные. API-брейков в нашем коде нет, все гейты зелёные.
- `event_listener 5.4.1 → 5.4.2` (RUSTSEC-2026-0221) — транзитивный, тривиальный.

**Зависимости — dev/build-only, в бандл не попадают** (бампнуты для чистоты отчёта, не
из-за runtime-риска — в приложении нет Node-рантайма, esbuild/vite не шипятся):

- `undici 7.28.0 → 7.29.0` — приходит через **jsdom** (только vitest).
- `postcss 8.5.20 → 8.5.25` — приходит через **vite/tailwind** (только сборка).

**Зависимости — принято по политике** (расписано в [deny.toml](src-tauri/deny.toml)):

- `rsa` Marvin-атака (CVE-2023-49092 / GHSA-4grx-2x9w-596c == RUSTSEC-2023-0071) — апстрим-фикса
  нет; митигируется предпочтением ed25519/ecdsa.
- `glib < 0.20.0` unsound (RUSTSEC-2024-0429 / GHSA-wrw7-89jp-8q8g) и семейство gtk-rs 0.18,
  `unic-*`, `proc-macro-error` — транзитив из Linux-стека WebKitGTK Tauri, нами независимо не
  апгрейдится.

**Код (SAST) — все находки ложные, кода не меняли** (недоверенного входа в этих путях нет):

- `scripts/set-version.mjs` — dev-скрипт смены версии, **не в бандле**. CWE-943 (запись файла,
  ×3): «вход» — аргумент CLI, который **валидируется** `/^\d+\.\d+\.\d+$/` до любой записи,
  а путь собран из **литеральных** констант; ни путь, ни содержимое не управляются извне.
  CWE-117 (log injection, ×2) — это `console.error`/`console.log` CLI-утилиты, а не запись в
  лог-файл; сообщение собрано из уже-валидированного semver.
- `src/lib/ui/util.ts` — CWE-400 на `setTimeout` в стандартном trailing-debounce; интервал
  задаётся внутренними вызовами (debounce ResizeObserver/resize), не входом извне.

## Hardening (что сделано)

- **CSP.** В `tauri.conf.json` задан строгий `csp` (и `devCsp` для Vite HMR):
  `default-src 'self'`, `connect-src 'self' ipc:` (никаких удалённых соединений),
  `object-src 'none'`. Удалённые источники скриптов/стилей/картинок запрещены.
  `script-src 'self'` без `'unsafe-inline'` (v1.25.1): inline-бутстрап SvelteKit и скрипт
  первого кадра темы проходят по sha256, которые сборка Tauri вписывает в `script-src` сама;
  `'unsafe-inline'` при хэше браузер всё равно игнорировал. В `img-src` только `'self' data:`.
- **Capabilities (наименьшие привилегии), поимённо.** `capabilities/default.json` не выдаёт ни
  одного набора `*:default` — с v1.25.1 и `core:default`, который открывал странице меню, трей,
  пути, картинки и все геттеры окна. Выдано: события (`listen`/`unlisten`/`emit`), имя и
  версии приложения (справка), кнопки окна безрамочного заголовка, `dialog:allow-open`/
  `allow-save` и `opener:allow-open-url` **со scope `https://*`** (без открытия путей/`reveal`,
  без message/ask/confirm-диалогов, без `fs`). Нет `dangerous*`-флагов. Список держит гейт.
- **WebView — граница доверия** (v1.25.1, [ADR 0036](docs/adr/0036-webview-trust-boundary.md)).
  Страница называет argv, бэкенд его проверяет: у каждого драйвера своя политика в Rust на
  обоих транспортах — git только подкоманды панели и ни одной опции, запускающей программу или
  пишущей файл (`--upload-pack`, `--receive-pack`, `--exec`, `--output`, `--config-env` и их
  сокращения); docker — программа `docker` и команды панели (без `run`/`exec`/`cp`/плагинов,
  `compose` без `-f`); kubectl — `kubectl`/обёртки и глаголы панели (без `exec`/`run`/плагинов,
  `--kubeconfig`, `--server`, учётных данных). `ai_exec` сам отказывает прод- и
  `noAi`-серверам по текущему профилю. **Остаточный риск — по замыслу продукта:** страница
  печатает в терминал пользователя и пишет файлы через SFTP и локальную панель, поэтому
  скомпрометированный WebView может набрать команду в открытой вкладке или переписать
  `~/.bashrc`. Граница закрывает тихое исполнение программы мимо терминала. На SSH
  `probe_run` передаёт `sh -c '<конвейер>'` (TLS-инспектор) — это сервер пользователя, как и
  его терминал.
- **Несколько окон** (v1.3, ADR 0017). Вкладку можно вынести в отдельное окно ОС — второй
  WebView. Новой поверхности снаружи это не добавляет, но внутри появляется обмен между
  окнами, и он устроен так:
  - окна создаёт **только Rust** (`appwin.rs`); у WebView нет разрешения открывать окна, а
    capability действует ровно на `main` и `win-*` — не на `*` (гейт `tauri-security.guard`).
    Второе окно получает те же минимальные права, что главное, и ни одного сверх них;
  - состояние вкладки едет **пакетом через IPC**, в памяти: в нём пароль вкладки, если он был
    набран, и sudo-пароли открытых редакторов. Бэкенд держит пакет в `Zeroizing`, отдаёт его
    только окну-адресату и один раз; в `localStorage` и на диск он не попадает;
  - с v1.4 (ADR 0018) тот же пакет может получить **уже открытое** окно — то, которое само
    назвало себя принимающим, и только одно: правила «в памяти, одному адресату, один раз» те
    же. Какое окно под указателем при перетаскивании, бэкенд спрашивает у ОС (`winhit.rs`):
    наружу при этом ничего не уходит, во фронтенд возвращается только метка **своего** окна
    или ничего — о чужих окнах приложение не узнаёт. Окну, над которым держат вкладку,
    пересылается лишь то, из чего рисуется её метка (вид, сервер, имя, статус, имя
    контейнера) — без пароля и без команды входа в контейнер; принимающее окно читает это
    как недоверенный ввод и оставляет только эти поля. Над рабочим столом вкладку показывает
    третье окно — метка (`drag-ghost`, `dragghost.rs`): создаёт его только Rust, capability
    на него не действует (она на `main` и `win-*`), его страница (`ghost.html`) статична, не
    зовёт ни одной команды и получает от бэкенда лишь имя вкладки, цвета и размер;
  - завершить сессию может только окно-владелец: `disconnect` от другого окна игнорируется;
  - рассылка настроек между окнами несёт то же, что лежит в `localStorage` (секретов там нет:
    ключи ИИ и пароли реестров — в keychain), и применяется той же очисткой, что импорт
    бэкапа.
- **Вкладки после перезапуска** (v1.6, ADR 0019). Открытые вкладки и раскладка центра
  пишутся в `localStorage` (`vterm.tabs:<окно>`) и читаются при следующем запуске:
  - в записи вкладки — только что это и где стояло: вид, id сервера, алиас, для вкладки
    контейнера — цель и argv входа. **Введённый пароль, статус и содержимое терминала в неё
    не попадают**: запись собирается по полям, а не копированием вкладки (гейт
    `tabrestore.guard`); вывод терминала не сохраняется вовсе;
  - **при запуске приложение ни к чему не подключается само**, пока это не включено
    настройкой; и тогда — никогда к прод-серверу, никогда во вкладку контейнера и никогда
    туда, где понадобится ввести секрет. В режимах «не восстанавливать» и «по кнопке» запуск
    не читает связку ключей;
  - сохранённое читается как недоверенный ввод: дерево областей перестраивается, id сессии
    проверяется по набору символов (он попадает в имена событий), вкладка с повреждённым argv
    не восстанавливается. **Принятый риск:** argv входа в контейнер лежит в `localStorage` и
    будет набран в шелл по кнопке «Войти» — тот, кто может писать в профиль пользователя,
    может его подменить. Граница та же, что у остальных настроек в том же хранилище (путь к
    `kubectl`, сниппеты): доступ к профилю пользователя — уже доступ к его сессиям.

  Остаточный риск: окна одного приложения доверяют друг другу. Скомпрометированный WebView
  одного окна (а CSP и экранирование недоверенного входа существуют, чтобы этого не случилось)
  может запросить вынос любой **своей** вкладки — в новое окно или в другое открытое — и
  разослать настройки остальным окнам; до сессий другого окна он через эти команды не
  дотягивается, а окну, которое вкладку получило, достаётся лишь то, что было в ней самой.
- **Секреты.** Пароли/passphrase живут в OS keychain (`secrets.rs`), не в файлах
  и не в логах (логирование секретов отсутствует). Копии в памяти оборачиваются в
  `zeroize::Zeroizing` и стираются при сбросе. Секрет пишется в keychain только
  **после** успешной аутентификации — поэтому галочка «сохранить» в окне секрета
  предложена нажатой: неверно набранный пароль сохранён не будет, а keychain и так
  единственное место, куда приложение вправе его положить. Это предложение, а не
  решение: снятая галочка уважается, и следующее окно снова открывается с дефолтом. **Пароль Docker-реестра** (Фаза 36, `vterm:registry`,
  ключ = url реестра) — тоже только в keychain: не в `settings.dockerRegistries` и не в
  бэкапе-экспорте (там лишь url+username), не в argv (`docker login --password-stdin` через
  `exec_captured_stdin`/stdin-pipe) и **не** в записи сессии (мутирующий docker-миррор
  логина не касается). На хост он уходит по зашифрованному SSH-каналу; сам docker может
  сохранить его на хосте в `~/.docker/config.json` (base64) — это вне контроля приложения.
- **Host-key.** Дефолтная политика — **TOFU с отклонением изменённого ключа**
  (`HostKeyPolicy::TofuReject`), не «доверять всему». Доступны `strict` и `accept`.
  **Сертификаты хоста не поддерживаются и отклоняются при любой политике** (с russh 0.63
  `check_server_key` может получить сертификат): доверенных CA у приложения нет, а пин
  вложенного ключа молча пропустил бы подпись, срок и principals. Алгоритмы
  `*-cert-v01@openssh.com` клиент не рекламирует, так что штатный сервер сертификат не пришлёт.
- **Вход `keyboard-interactive`** (v1.0.38). Сохранённый пароль уходит только в **скрытый**
  вопрос сервера, похожий на запрос пароля, и один раз за вход (`kbdauth::plan`); в поля
  одноразовых кодов он не попадает, после частичного успеха (ключ/пароль + код) повторно не
  шлётся. Ответы на остальные вопросы — только в памяти (`Zeroizing`), не в keychain, записи
  сессии и логах. Текст вопросов приходит от сервера и показывается как текст (без разметки).
  **Остаточный риск:** враждебный сервер может сформулировать скрытый вопрос как «Password:» и
  получить пароль — ровно как при методе `password`, которым мы его и так бы отправили; поэтому
  это не новая поверхность. Опознание вопроса — по словам, на неизвестном языке пароль не
  подставится и будет спрошен у пользователя (сдвиг в безопасную сторону).
- **Ошибки.** Типизированы (`AppError`), без утечки секретов в сообщениях.
- **Проверка доступа с локальной вкладки** (v1.0.36). Единственное место, где приложение
  само открывает соединение не по SSH: TCP-рукопожатие к хостам и портам, которые
  пользователь ввёл и отправил кнопкой. Соединение сразу закрывается, без полезной нагрузки;
  не больше 2048 проверок с одного хоста за прогон; бэкенд сам отклоняет хосты с пробелами и
  управляющими символами (они подделали бы строки протокола ответа). Остаточный риск — утилиту
  можно использовать как небольшой сканер портов с машины пользователя; это ровно то, что уже
  умеет `nc` в его терминале. Сокеты вне `ssh.rs`/`netcheck.rs` ловит Rust-гейт.
  [ADR 0012](docs/adr/0012-local-access-check.md).
- **Проверка подсети и с нескольких серверов** (v1.21). Цель-подсеть разворачивается в каждый
  адрес хоста, и прогон идёт с серверов, которые назвал источник заявки, — по их сессиям. Это
  обход сети, который видят системы обнаружения вторжений, поэтому он не начинается без
  подтверждения со счётом соединений по серверам (у прод-сервера — красное предупреждение),
  ограничен 2048 соединениями с сервера, останавливается на сервере (`SIGTERM` и закрытие
  канала) и пишется в запись сессии каждого сервера итогом, а не сырым протоколом. Принятый
  риск — тот же, что у `nmap` в терминале пользователя на этом сервере.
  [ADR 0032](docs/adr/0032-access-check-requests.md).
- **Инструменты пользователя в проверке доступа на этой машине** (v1.22). По выбору плитки
  `netcheck_run` запускает локально `bash`, `nc`, `telnet` или `curl` — но страница передаёт
  только **имя** инструмента (`LocalTool::parse`), а argv зашит в Rust (`LocalTool::argv`).
  Иначе скомпрометированный WebView получил бы `bash -c '<что угодно>'`: allowlist программы
  без проверки аргументов, как у `curl`/`openssl` в `probe_run`, здесь не годится. Хост —
  отдельный аргумент (у `bash` — `$0`, не текст команды), бэкенд не пускает хост с `-` в
  начале и с чем-либо, кроме букв, цифр, `.`, `-`, `_` (опция `nc`, `user@host` у `curl`).
  Без шелла, через `localenv`, без окна консоли, ожидание ограничено (процесс убивается), по
  «Остановить» — убивается сразу. На Windows — только `curl`. Остаточный риск — тот же, что у
  `nc` в терминале пользователя. Гейт `a_local_tool_runs_only_its_fixed_argv`.
  [ADR 0033](docs/adr/0033-access-check-picked-servers-local-tools.md).
- **TLS-инспектор и HTTP-клиент с локальной вкладки** (v1.0.41). `probe_run` на локальной
  вкладке запускает процесс на машине пользователя — поэтому только `curl` и `openssl`
  (allowlist `netprobe::local_program_allowed`, по имени программы), без шелла, аргументы
  verbatim, только по кнопке. `sh`/`cmd`/`powershell` отклоняются: иначе скомпрометированный
  WebView получил бы произвольный локальный процесс через утилиту. Остаточный риск — `curl`
  с аргументами из WebView умеет писать файлы (`-o`) и читать их (`-d @file`); это та же
  поверхность, что у `docker`/`kubectl` локальных панелей, а граница здесь — CSP и
  недоверенный вход, не allowlist флагов. Сокетов приложения не добавилось.
  **Запись сессии** (v1.0.42): раньше `probe_run` писал туда сырой argv и весь ответ — значения
  `Authorization`/`X-Api-Key`, тело запроса с паролем, тело ответа и `Set-Cookie`. Теперь
  исполнители в запись не пишут (Rust-гейт), а итог собирает фронт: значения заголовков
  маскируются все, кроме короткого списка безвредных (`Content-Type`, `Accept`…), URL и текст
  проходят `redactSecrets`, тела — только размером. Управляющие символы из ответа сервера
  вычищаются (`netprobe::audit_block`), чтобы враждебный хост не управлял плеером записи.
  [ADR 0014](docs/adr/0014-local-tls-http-probes.md).
- **Имена файлов с сервера** (v1.11.3). Листинг каталога и листинг хэшей для синхронизации —
  слова сервера. Враждебный или взломанный сервер мог назвать файл `../../.ssh/authorized_keys`
  или абсолютным путём: скачивание папки склеивало имя с выбранным каталогом и писало за его
  пределами, и прогон синхронизации скачивал такой файл так же. Теперь
  локальный путь из такого имени строится только через проверку (`localfile::safe_child` /
  `safe_join`): одна компонента, без разделителей, не `.` и не `..`; на Windows ещё без `\`,
  `:` и хвостовой точки или пробела. Скачивание папки на таком имени останавливается, путь
  листинга хэшей в план не попадает, а `sync::apply` проверяет каждый путь плана до любого
  действия: план возвращается через WebView, и в нём, в отличие от листинга, может стоять и
  удаление. Держит Rust-гейт
  `local_paths_from_server_names_are_checked`. **Остаточный риск:** символьная ссылка внутри
  локальной папки ведёт запись туда, куда указывает, — это дерево пользователя, его ссылки не
  проверяются. Одиночное скачивание идёт по пути, который пользователь выбрал в системном
  диалоге, и имени сервера не доверяет.
- **Копия между серверами** (v1.12). Файл с одного сервера на другой идёт через процесс
  приложения: читается по SFTP одной сессии, пишется во временный файл по SFTP другой и
  переименовывается поверх цели. На диск этой машины он не попадает — файл прод-сервера не
  остаётся на ноутбуке ни целиком, ни куском после сбоя. Серверы не получают ни ключей, ни
  адресов друг друга: каждый говорит только с приложением. Имя из листинга одного сервера не
  доверяется на другом (`sftp::safe_child`): иначе враждебный источник писал бы на сервере
  назначения за пределами выбранной папки — правами сессии пользователя. Новый файл получает
  биты прав источника (без setuid/setgid/sticky), чтобы секрет с `0600` не стал читаемым.
  Имя вкладки, которое попадает в запись другой сессии, приходит из WebView и очищается до
  букв, цифр и `._@-`. **Остаточный риск:** содержимое файла проходит через память
  приложения блоками по 32 КБ и нигде не сохраняется, но и не проверяется — копируется то,
  что отдал источник.
- **Перетаскивание файлов между окнами и с рабочего стола** (v1.13). Окно, над которым
  держат файлы из другого окна, узнаёт о них от бэкенда, а тот передаёт слово первого окна
  как есть. Сообщение читается, а не принимается на веру (`parseFiles`: тип каждого поля,
  непустые пути и имена, не больше 2000 объектов) — как и список сессий других окон
  (`foreignTargets`). Копия начинается только после диалога с папкой назначения в окне,
  которое её принимает. Пути файлов, брошенных на локальный терминал, вписываются в него
  через `term.paste()` в кавычках той оболочки, что там запущена (`quotePaths`); путь с
  переводом строки или невыразимый в этой оболочке не вписывается вовсе, и перевода строки
  в конце нет — вписанное не исполняется само. **Остаточный риск** прежний: окна одного
  приложения доверяют друг другу в том, какую сессию назвать источником.
- **Вынос файла в систему** (v1.14, ADR 0027). Имя файла — слово сервера, и здесь оно
  уходит **чужой программе** как имя создаваемого файла: обещается только имя из одного
  безопасного компонента (`promised` → `localfile::safe_component`), на Windows из него
  ещё заменяются знаки, недопустимые в имени. Длину файла странице называть не дано — её
  говорит сервер. На время перетаскивания приложение выставляет другим процессам COM-объект
  данных (Windows): он отдаёт только описание и содержимое обещанных файлов и ничего не
  принимает (`SetData` — отказ). Сбой чтения с сервера доходит до принявшего ошибкой, а не
  концом файла. В запись сессии уходит `[sftp] get … -> (dragged out)` (Windows) или
  обычная запись задания (macOS). **Остаточные риски:** на Windows программа, над которой
  файл пронесли, может запросить его поток и прочитать файл без броска — так устроено
  перетаскивание в OLE (скачивание начинается только с первого чтения, не с выдачи
  потока); куда лёг файл и что он там заменил, решает Проводник, и в записи сессии места
  назначения нет; содержимое, как и при любом переносе, не проверяется.
- **Недоверенный markdown** (Фазы 44.3–44.6). Рендерер разметки писался под встроенную
  инструкцию, а со временем стал показывать ответы LLM, AI-планы, заметки и **любой `.md`,
  открытый на сервере**. Ссылка вида `[x](javascript:…)` в любом из этих мест исполняла код
  в окне, у которого есть `invoke()` ко всем командам. Защит теперь **две, и каждая
  проверяет схему независимо**: allowlist схем при построении `href` (отклонённая ссылка
  рисуется текстом) и экшен `use:mdLinks`, который давит навигацию и отдаёт `http(s)`
  системному браузеру — у окна нет адресной строки, поэтому переход WebView неотличим от
  самого приложения. Картинки рисуются только из байтов, которые прочитали мы сами
  (`data:`), удалённые URL не грузятся никогда — иначе враждебный `.md` узнавал бы, когда и
  откуда его открыли. Raw-HTML проходит санитайзер по фиксированному allowlist (без
  `on*`/`style`/`<script>`/`<iframe>`), включён **только** в превью редактора. Подробности —
  [ADR 0008](docs/adr/0008-untrusted-markdown.md).
- **Ссылки в выводе терминала** (v1.20). Вывод пишет сервер, а у OSC 8-гиперссылки текст и
  адрес заданы порознь: взломанному хосту достаточно напечатать `github.com` поверх ссылки
  на свой сайт. Такие ссылки уходили в обработчик xterm по умолчанию — английский
  `confirm()` и `window.open()` в обход opener; так же было в проигрывателе записей, а
  записи приходят и из чужих бэкапов. Теперь любая ссылка из вывода идёт через один путь
  (`clickLink`): по умолчанию — вопрос с хостом, к которому подключится браузер (punycode
  для нелатинского имени), и адресом, где выделен хост, а не `user@` перед ним. Ссылка, чей
  текст называет другой сайт, спрашивает и в режиме «Открывать сразу». Открывается только
  `https` — scope opener не менялся. **Остаточный риск:** в режиме «Открывать сразу»
  ссылка, текст которой не похож на адрес («документация»), открывается без вопроса;
  сравнение хостов — по имени, а не по владельцу сайта.
- **Файлы в выводе терминала** (v1.24, [ADR 0035](docs/adr/0035-file-links-in-terminal-output.md)).
  Имена в выводе пишет сервер, и клик по ним открывает файл — значит, вывод решает, какой
  путь прочитает приложение. Защита: ссылкой становится только имя, которое есть в листинге
  каталога его команды; каталог берётся в момент отправки строки и только если строку
  получил сам шелл (иначе — неизвестен, а не «текущий»); шелл контейнера ссылок не даёт;
  по умолчанию — вопрос с сервером и полным путём, у прода — красная пометка. Открытие
  только читает файл в редактор тем же путём, что панель файлов; ничего не исполняется.
  Наведение на строку SSH-вкладки читает листинг каталога по SFTP открытой сессии.
  **Остаточный риск:** `cd x && ls` в одной строке читается в каталоге до `cd`; программа,
  которая сама печатает чужие имена (не листинг), может совпасть с именами каталога, — путь
  в вопросе это показывает.

## Аудит ИИ-агента (Фаза 20)

Верификационный adversarial-проход по самой опасной поверхности — ИИ-агенту,
исполняющему shell-команды по указке внешнего LLM. **Границы безопасности** здесь —
prod/noAi-гейт + согласие (consent) + маскирование (redaction); эвристика опасных
команд — лишь дополнительный предохранитель (принуждает подтверждение), **не**
граница.

- **Deny-list опасных команд** (`aidialog.ts`, `isDangerousCommand`). Расширен
  против обходов по форме флагов и обфускации: длинные/раздельные флаги `rm`
  (`--recursive --force`, `rm -r -f`), `--no-preserve-root`, `find … -delete`/
  `-exec rm`, пайп в шелл (`curl … | sh`), `base64 -d`/`--decode`, `eval`,
  рекурсивный `chmod/chown -R` на корень `/`. Bias — over-flag: ложное срабатывание
  = лишний confirm, не блокировка. Закреплено `aidialog.test.ts`.
- **Маскирование секретов** (`redact.ts`). Добавлены standalone self-identifying
  токены, которые утекали вне `KEY=`/`Bearer`-контекста: JWT (`eyJ…`), GitHub
  (`ghp_`/`github_pat_`), Slack (`xox…`), Stripe (`sk_live_…`), GCP (`AIza…`),
  Google OAuth (`ya29.…`). Закреплено `redact.test.ts`.
  **Остаточный риск (best-effort):** PuTTY `.ppk`-ключи и произвольные многострочные
  base64-блобы не распознаются автоматически. Смягчение: consent-диалог всегда
  показывает пользователю пост-redaction текст перед отправкой.
- **Прод-гейт** (`isProdServer`, `noAi`). Источник — явный флаг профиля `prod`; тег
  `prod`/`production` учитывается только у профиля без флага (сохранённого до v1.0.37) —
  регистронезависимо и с обрезкой пробелов, контракт **точного тега** намеренный
  (`prod-eu`/`non-prod` **не** prod, иначе non-prod-серверы потеряли бы диалоговое
  исполнение). Наследования
  prod/noAi через папки-группы **нет** (папка — строковая метка).
  **Остаточный риск:** флаги `prod`/`noAi` снимаются в снапшот при старте диалога и
  не перечитываются на каждом шаге feedback-цикла — смена флага `prod`/выставление `noAi`
  **во время** активного авто-диалога не прерывает уже идущий цикл (следующее
  сообщение пользователя пересчитывает флаги). Смягчение: авто-диалог ограничен
  лимитом шагов, каждый шаг зеркалится в терминал/запись, опасные команды всё равно
  требуют подтверждения. Надёжный фикс требует поддержки прерывания между шагами в
  сторе `aichat` — вынесено в бэклог.

## Принятые исключения (advisories)

Исключения задокументированы в [src-tauri/deny.toml](src-tauri/deny.toml). Исключение,
которому больше нечего исключать (advisory закрыт обновлением или отозван), и разрешённая
лицензия, которой никто не пользуется, роняют `cargo deny`
(`unused-ignored-advisory`/`unused-allowed-license`) — гейт `tauri-security.guard.test.ts`. Lockfile освежается `cargo update`
перед выпуском: Dependabot двигает только прямые зависимости, а исправления транзитивных
приходят именно так.

- **RUSTSEC-2023-0071 (`rsa`, Marvin timing side-channel).** Фикса вверх по
  течению **нет**. Доходит до нас только через поддержку RSA в `russh`.
  **Снижение риска:** используйте ключи **ed25519/ecdsa** (vterm их поддерживает) —
  тогда RSA-путь не задействуется. Снять исключение, когда выйдет патч `rsa`.
- **proc-macro-error (RUSTSEC-2024-0370)** — unmaintained, приходит через `glib-macros`
  gtk-rs 0.18: Linux-стек WebKitGTK самого Tauri, нами не обновляется. **glib
  (RUSTSEC-2024-0429)** — `unsound` из того же стека: оба инструмента показывают его
  предупреждением и не падают, поэтому в исключения он не внесён; `VariantStrIter` мы не
  вызываем. gtk-rs-advisory RUSTSEC-2024-0411…0420 RustSec отозвал 2026-08-14, `unic-*`
  (RUSTSEC-2025-0075/0080/0081/0098/0100) ушли из дерева с Tauri 2.12 (`urlpattern` 0.6) —
  оба набора исключений сняты в v1.25.0.
- **zvariant, zbus_names, zvariant_derive (RUSTSEC-2026-0370…0372).** Unmaintained, потому
  что влиты в `zbus` 6.0; это смена статуса, а не уязвимость, исправленных версий не будет.
  Linux-only: `zbus` 5 под `keyring` (Secret Service) и плагинами Tauri `opener` и
  `single-instance`. Снять исключение, когда они перейдут на `zbus` 6: сам `zbus` 6 уже
  стабилен, но `secret-service` 5.2 и плагины 2.x на 2026-10-28 ещё на `zbus` 5.
- **npm, уровень low (не блокируют CI: `pnpm audit --audit-level moderate`).** `deepmerge`
  ≤ 4.3.1 (GHSA-gcqx-w48m-w2h4, загрязнение прототипа в `mergeObject()`) — сборочная
  зависимость `@sveltejs/vite-plugin-svelte`, в бандл не попадает; исправленной версии нет
  (последняя — 4.3.1), override поставить не на что. Два advisory `@sveltejs/kit` < 3
  (GHSA-pfhg-q3qv-9q6r — редирект через enhanced form, GHSA-27mw-82g8-phjj — XSS через
  `cache-control` пререндеренной страницы) закрыты переходом на SvelteKit 3 в v1.25.7; с ним
  снят и override `cookie` `^0.7` — Kit 3 сам зависит от исправленного `cookie` 2.
- **`zip` (RUSTSEC-2026-0367…0369)** — не исключение: закрыты обновлением до `zip` 9. vterm
  `extract()` не вызывал — записи бэкапа читаются по одной, имя проверяет
  `safe_recording_name`.
- **Trivy DS-0002 (`root` в образе) — только `e2e/kbdint/Dockerfile`.** Тестовый sshd для
  живых тестов входа `keyboard-interactive`: sshd обязан работать от root, чтобы переключиться
  на входящего пользователя; контейнер локальный и живёт на время прогона. Исключение — в
  [.trivyignore.yaml](.trivyignore.yaml) с `paths` на этот файл, чтобы не глушить правило для
  будущих Dockerfile; порт внутри непривилегированный, HEALTHCHECK есть.
- **Trivy DS-0026 (нет `HEALTHCHECK`) — только `e2e/linux/Dockerfile`.** Linux-контейнер
  разработчика ([linux-box.sh](scripts/linux-box.sh)) выполняет одну команду — сборку или
  E2E-набор — и выходит с её кодом: он ничего не обслуживает, и проверять у него нечего.
  Исключение — там же, с `paths` на этот файл. Работает он от обычного пользователя, не от
  root: исключения для DS-0002 у него нет.

## Канал обновлений

По явному запросу приложение обращается к GitHub Latest и ассетам официального репозитория.
Новая поверхность — HTTPS-метаданные, архив приложения и отдельный процесс установки.
Подписанный Ed25519 манифест связывает версию, формат, архитектуру, размер и SHA-256 артефакта;
помощник повторяет проверку после выхода приложения. В клиенте только открытый ключ.
Сетевые размеры ограничены, редиректы разрешены только хостам GitHub, ZIP-пути и символические
ссылки не принимаются. Подпись канала не является Developer ID/Authenticode и не гарантирует
отсутствие предупреждений ОС.

Помощник не работает постоянной службой и не получает общий привилегированный API. Пакеты
передаются штатным установщикам с их запросами прав. Локальный злоумышленник с правами
пользователя, способный менять сам vterm или его приватный каталог подготовки, остаётся за
пределами защиты канала. Повышение прав при произвольной замене файлов не реализовано.
При сбое питания между переименованиями может потребоваться ручное восстановление из
`.vterm-previous`; миграции данных и пакетные установки не откатываются простой заменой файла.
